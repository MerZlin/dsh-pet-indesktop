# 计划、汇报与四份留档规范

适用：本项目所有正式工程计划和阶段汇报。入口：[工程指南](../../AGENTS.md) · [文档索引](../INDEX.md)；配套：[交接规范](handoff.md) · [本次落地设计](WORKFLOW-STANDARDIZATION-2026-09-30.md)。本文件是详细模板的唯一维护位置，其他规范引用它，不复制另一套规则。

## 1. 总原则

- 先复述目标，区分当前事实、待实施方案和已获授权的范围；重大范围变化先确认。
- 前面使用正式工程说明，最后用直白语言说明实际体验，不用内部拆分数量代替交付效果。
- 不开子智能体。只有用户后续明确改变这一约定时才重新讨论。
- 提交、推送、发布分别按当次授权执行；一次推送授权不等于未来自动发布授权。
- 保留已有工作树改动，按主题小步验证、可回滚；不以新结论覆写历史证据。
- 本规范不降低现有 PR 证据、推送前验证、数据保护或文档登记要求。

## 2. 正式计划固定结构

### 2.1 正式工程部分

每份正式计划至少包含：

1. **目标与当前事实**：用户目标、仓库/版本基线、已实现与待验收状态；历史检查注明日期及版本。
2. **范围与非目标**：本轮修改边界、保护文件、授权范围，哪些工作明确留到后续。
3. **方案和合同**：接口、所有权、行为/数据/生命周期变化、兼容与降级，不把设想写成现状。
4. **实施顺序**：稳定任务编号、依赖关系、每步产出、进入下一步的条件。
5. **风险与停止条件**：替代方案、既有失败、环境约束，以及何时暂停而不是继续打补丁。
6. **验收与回滚**：命令、环境、预期结果、人工项、证据位置、对应提交的回滚方式。
7. **四份留档的位置与状态**：同一任务延续同一组文件，说明是否已写入磁盘。
8. **完成后的实际使用效果**：固定放在最后，采用下文模板。

### 2.2 计划结尾模板

```text
## 完成后的实际使用效果

- 用户届时能看到/操作什么：……
- 原有操作是否变化：……
- 本步只是内部基础设施时：暂时没有新增用户操作；它解决的是……
- 涉及插件时：能否关闭、是否已可卸载、文件属于 Core 还是功能包；
  Core/host/Worker 怎样连接，安装与卸载是否真的可用。
- 当前限制和后续目标：……（明确不是本轮已完成能力）
```

涉及可选功能时分别验收：独立 Worker、功能开关、物理可卸载。不能把“另起一个进程”描述成“安装卸载已经完成”。

## 3. 每次汇报固定结构

使用以下顺序；小改动可以简写，不能省掉事实状态和结尾限制：

1. **当前判断**：本轮所处阶段和真实完成度。
2. **本轮目标**：做什么、不做什么。
3. **已执行命令与结果**：实际命令、环境、退出码/数量，失败分类；未执行的不要填绿灯。
4. **修改文件清单**：逐文件或同职责分组说明内容与原因；PR 仍遵守逐文件证据要求。
5. **验收结果**：已通过门、未通过门、尚未执行项，不能用历史结果代替本轮验证。
6. **需要确认的事项**：没有则明确写“无新增确认项”；风险或范围变化不能藏到结尾。
7. **下一步**：准确任务编号/命令/编辑位置；本轮完成时注明是否还有后续阶段。
8. **本次实际可体验的效果与限制**：用户现在能用什么、操作是否变、安装卸载是否可用、哪些尚未交付。

## 4. 四份记录：职责与更新时机

| 记录 | 权威职责 | 位置 | 更新时机 |
|---|---|---|---|
| 设计与验收详情 | 目标、边界、接口、方案、验收矩阵、风险和回滚 | 对应阶段 `docs/`；工程规范任务可在 `docs/agents/` | 正式计划确定或范围改变时 |
| `PLAN.md` | 稳定编号任务、依赖、勾选状态及完成证据引用 | `.scratch/<任务名>/` | 每个子步骤完成后 |
| `HANDOFF.md` | 精确停点、最近一次验证、阻塞与下一条操作 | 同上 | 暂停、阶段结束、上下文交接前 |
| `STATUS.md` | 当前阶段、验收门、人工待办、提交及远程同步摘要 | 同上 | 阶段、验证或 Git 同步状态变化时 |

四份记录都纳入 Git 并登记 [INDEX](../INDEX.md)。三份任务文本不复制整份设计；记录之间互链，状态引用任务编号和证据。沿用已有任务文件，不为每次对话再建一套。现有仅有 `spec.md` 的本地 ticket 不必批量搬迁；下一次正式阶段计划确定时建立权威设计链接，避免两个方案同时有效。

### 4.1 首次落盘与忽略目录

- 正式计划已获执行授权后，**先留档，再实现**。
- Plan Mode 无法写入时标记“待落盘”；进入执行模式后再创建，不声称已经保存。
- `.scratch/` 可以继续忽略生成物；仅显式加入三份任务 Markdown，必要时逐文件 `git add -f -- <明确文件>`。
- 不用 `git add -A`、`git add .` 或对整个被忽略目录强制加入。
- 原始日志、缓存、截图、安装包、测试私钥和用户数据不随“全部成果”入库。入库证据保留命令、环境、结果和可复现方式，而不是依赖未跟踪文件的链接。

### 4.2 最小记录模板

```text
PLAN.md
  更新日期；设计 / STATUS / HANDOFF 链接
  - [ ] T01 任务、依赖、通过条件
  - [x] T02 任务；证据位置、实际结果
  停止条件与未完成项

HANDOFF.md
  工作区、分支、准确停点；已确认决策
  最近一次真实验证：命令、版本、结果、失败分类
  TDD 最后 red/green；不适用（如纯文档）时明确说明
  修改/未跟踪范围、提交与远程状态
  下一条命令或编辑位置；阻塞和不能重新打开的边界

STATUS.md
  更新日期；设计 / PLAN / HANDOFF 链接
  当前总体阶段和任务编号
  验收门：已通过 / 失败 / 未执行
  人工待办：未测 / 用户确认（注明对应版本）
  Git：已提交哪些、实际已核验推送到哪个提交、尚未同步哪些
  下一步；限制
```

### 4.3 完成与交接

当前状态及时替换，不追加整段聊天历史；历史失败与验证仍保留在日志或证据报告中。任务完成后保留四份记录和最终交接，注明“已完成、无剩余执行步骤”，另列后续阶段，不删除交接文件。

提交 SHA 无法写入自身提交：在随后独立记录提交回填实际 SHA，不 amend、不重写历史。记录的是已核验检查点，不递归追写自己的 SHA。推送后才写“已推送”，且注明核验到的提交；后续纯记录提交仍须实际推送并核对，不能预写成功。

## 5. 事实和验证纪律

| 状态 | 最低证据 | 不能推导出的结论 |
|---|---|---|
| 计划 | 已确认设计、待办及留档状态 | 不代表代码存在 |
| 已实现 | 实际文件/接口与差异 | 不代表测试或手测通过 |
| 自动化通过 | 对应版本、命令、环境与真实输出 | 不代表可见桌面或用户验收完成 |
| 实机通过 | 指定平台/构建上的真实运行证据 | offscreen 不能代替可见桌面操作 |
| 用户确认 | 用户明确反馈，限定功能与版本 | 旧版手动通过不代表新版自动通过 |
| 已提交 | 本地实际 SHA 和范围 | 不代表远程可见 |
| 已推送 | 远程分支 SHA 已与目标本地提交核对 | 不代表 CI、PR 合并或发布完成 |

- 历史结果必须注明版本/日期，不冒充本轮运行。引用构建产物还需说明与源码的对应关系。
- 未手测、不愿等待、环境未就绪不等于产品故障；也不能标为验收通过。
- 失败分为**既有问题 / 新引入问题 / 环境问题**；不能确认时先写“待分类”，给出证据缺口，不臆断。
- 任一硬门失败即停止相应提交/推送或下一阶段；不降阈值、删断言或沿用旧绿灯掩盖失败。
- 不为证据擅自读取真实密钥、截图、请求收费模型或进行长期 soak。
- 产品文案和历史证据各司其职：分支等执行元数据写进任务交接，不为消除扫描报错改写真实历史或放宽测试。

## 6. 实际使用效果与限制

本规范不会改变桌宠界面，也不会新增安装/卸载按钮。你可以从 `STATUS.md` 看当前进度，从 `PLAN.md` 看剩余工作，从 `HANDOFF.md` 找到继续执行的位置；每次计划和汇报最后都会说明“到底能怎么用”。功能交付仍须逐项通过自己的验收门，规范留档本身不是功能实现。
