## 1. 读表规则与代码核对依据

必须分别记录：**运行边界、功能开关、独立交付、物理卸载**。独立 Worker 只证明第一项；在 GUI 进程运行的功能 UI/策略/适配器也可以随官方功能包交付，不因此永久属于 Core 安装包。

本轮交叉阅读了以下入口，而非把每个 Python 文件机械地变成插件：

- [菜单分派](../../pet/context_menu.py)、[菜单动作模型](../../pet/context_menus/registry.py)及现代菜单的可用动作筛选；
- [设置导航与各功能区域](../../pet/modern_settings_dialog.py)、[配置领域 facade](../../pet/config_domains.py)；后者尚不等于各功能已独立迁移配置；
- [主动识屏策略](../../pet/proactive.py)、[识屏 Worker](../../pet/workers/proactive_screen_worker.py)、[窗口交互](../../pet/window.py)；
- [ChatService](../../pet/chat/service.py)、[会话存储](../../pet/chat/session_store.py)、[文本文件解释](../../pet/file_interpret.py)、[模拟投喂](../../pet/file_eater.py)；
- Phase 1 资源 Registry/ContentManager、Phase 2 官方节日提醒以及 Phase 3A Agent Link 的交付文档。

**11 个领域不是 11 个 ZIP，也不是 11 个 Worker。** 可以合包或共用受管理运行时，但不得因此隐藏专属依赖、循环依赖或无法独立关闭的功能。现有 `official.festival-reminder` 等 ID、配置键和用户数据不因本表分类而改名。最终包格式、ID、执行产物、共享依赖和安装路径由 Phase 4A/5A 的构建与迁移审计决定。

| 多实例协调 | 实例/角色窗口管理、碰撞 IPC、共享子系统协调、安装占用协调宿主 | 各功能自己的会话、事件采集和跨窗口结果策略 |
| 通用呈现 | 气泡、系统通知、动作请求、已有音效播放原语、音频通道与时隙仲裁 | TTS Provider/合成缓存、语音报时策略；`speak` 端口可以有可选提供者 |

| 数据与权限 | Core 配置、实例隔离、迁移/备份恢复、安全存储访问端口、授权与安装状态 | 业务会话/余额/识屏历史以及完整 Provider 实现；不存普通明文密钥 |

上述是最终 Core 归属，不表示当前 `PetWindow`/`AppShell` 已经没有业务耦合。公共 Core 帮助/项目链接、退出和基础窗口命令留在 Core；外部服务入口随相关功能，不能凭当前菜单位置决定归属。

## 6. 不可省略的独立使用场景

1. 只装 Core + 角色：离线基础行为正常，没有 AI、识屏、音乐、Agent 等后台任务。
2. 只装屏幕理解：能够自行配置视觉服务，不要求安装聊天；聊天同步是可选扩展。
3. 只装 AI：对话/会话/支持的文本文件解释正常，不依赖灵动岛或识屏，安装聊天不授予截图权限。
4. 提醒没有语音包：仍文字通知；日常台词无需网络与 AI Key。
5. Agent 没有余额包：事件与基础状态正常，账户估算/查询入口不注册。
6. AI 文件解释与模拟投喂可分开使用。当前解释面向已有文本/代码等白名单，不扩展承诺为通用 PDF/二进制解析平台。

共享视觉或模型协议可以抽为受控依赖，但不因此把完整 AI Provider/Chat UI 留回 Core。跨包同步使用端口/事件和能力检查；缺少消费者时安全不操作。

## 8. 最终效果，直白地说

- 本体负责“让桌宠活着、能操作、能管理扩展”，完整角色是资源包，聊天、识屏等是另外选装的官方功能。
- 先把“屏幕理解”真正拔得掉，再重点拆 AI 对话与文件理解；其他领域都在清单内，不会因为没提到就永久混进本体。
- 功能可以同时有主进程 UI 和独立 Worker；后者通过受控 IPC 与宿主连接，并非断开连接的独立桌面程序。
- 未来 Setup 可选旁置包、ZIP 可导入本地包，桌宠内能卸载；普通安装与显式便携的数据位置由 Phase 4A/5A 确定，不要求现在手动复制源码。
- **这些是待实现的交付体验**。当前内置 Worker 不需要单独安装，也还不能当作本表所说的功能 DLC 物理卸载。
