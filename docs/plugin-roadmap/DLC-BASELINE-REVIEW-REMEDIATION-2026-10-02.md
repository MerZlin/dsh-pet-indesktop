### 2.3 当前仍未解决的 P0 问题

#### P0-A：安装后资源根与 Registry 解析根可能不一致

当前代码静态风险链为：

```text
ContentManager.install()
→ characters/<id>/versions/<version>/
→ CharacterRegistry._package_from_root(root)
→ 已安装版本根可能再次追加 characters/<id>
→ Registry 解析失败，播放找不到资源
```

后续必须增加目录包和 ZIP 包两条真实链路：安装成功后由 Registry 解析，加载真实视频/资源，重启、激活和回滚后仍可播放。只检查 `active.json` 不算通过。

#### P0-B：冲突安装异常清理可能误删旧版本

异常清理使用的 `active_version(...)` 参数语义需要与角色/插件 ID 严格区分。必须证明：同版本不同内容冲突不会覆盖或删除旧 active；清理只能删除本次创建且有明确操作归属的 staging；故障注入后旧摘要和实际播放保持不变。

#### P0-C：Phase 1 暂不能称为发布级闭环

在 P0-A/B、Starter/Core 更新不变量和资源安装→Registry→播放 E2E 通过前，现行说法统一为：

> Phase 1 已有角色资源 DLC 基础实现，但安装后解析和冲突清理硬门尚未封存。

#### P0-D：Starter DLC 与 Core 更新保护不变量未封存

必须明确并测试 Starter 是 Core 内置 fallback 还是独立资源包；Core 更新成功、失败、回滚都保留 Starter 可用；用户角色包不会被 Core 更新删除；资源 fallback 不会复活已卸载的功能包。

#### P0-E：安装/卸载/中断恢复缺少真实资源链路

4B-1 状态账本不能替代 `安装资源 → Registry → 实际播放 → 停用 → 中断卸载 → 恢复 → 重装`。本地资源事务必须在远程 catalog 或第三方生态之前完成。

### 2.4 未在当前树复现但要保留防线

评审提到的具体 `frameseq` 派生缓存路径在当前仓库搜索中没有复现，因此不把该具体缺陷写成已存在或已修复。但底层风险成立：内容根目录的发布文件与派生缓存必须分离，缓存不得进入 manifest 摘要、激活版本目录或安装包清单。后续以通用缓存/hash 回归保护，而不是照搬未复现路径。

## 3. 评审提出的架构边界，已纳入后续合同

- **进程隔离不是安全沙箱**：Worker 与 Core 默认同一 OS 用户权限；`PluginContext`/capability 只限制 API 访问，不防止 Python 代码读文件、阻塞、死循环或 native crash。第三方 Worker 需要签名、权限声明、能力 allowlist 和故障隔离，不能把 `QProcess` 宣称为权限边界。
- **事件总线不是全面隔离**：能捕获的回调异常可以诊断，但不能保证阻止无限循环、阻塞 I/O、内存耗尽或 native 崩溃。
- **身份分层不能只写“实例=进程”**：后续合同使用 `data_root_id`、`config_slot_id`、`window_id`、`process_id`、`host_id`、`service_id`、`worker_id`，并说明权限和数据所有者。
- **包类型语义不能混写**：纯资源包不执行代码；官方 host/Worker 需要受控可信加载；远程 catalog 另有新鲜度、签名和回滚合同。

### Phase 1 P0 / Phase 4B-1.5 资源加固门

4B-1.5 已完成窄范围代码修复与自动化验证，阶段封存和对外承诺仍需独立核对。在任何 Phase 5 远程分发或 Phase 6 第三方开放前必须完成：

2. 修复冲突安装异常清理；
3. 目录/ZIP 安装→Registry→真实播放→重启/激活/回滚 E2E；
4. Starter/Core 更新成功、失败和回滚保护；
5. 内容发布根与派生缓存根隔离；
6. 中断卸载可恢复且不复活已卸载功能。

### Phase 4A/4B 加固顺序

- Phase 4A 继续完成通用端口、官方 host、受控加载和独立构建；不把 capability 当沙箱。

## 6. 失败重启点

- P0-A/B 失败：保留 Phase 1 代码和 legacy fallback，回到 `ContentManager + CharacterRegistry` 真实播放边界；不进入远程分发。
- P0-D 失败：保留 Starter/legacy/Core fallback，但禁止宣称 Core 更新安全。
- 4B-1 失败：保留状态账本的只读/禁用恢复路径，禁止租约、删除和管理 UI假设成功。
- 4B-2/4B-3 失败：继续允许 Core 启动，功能包保持禁用或待恢复，不回到目录扫描猜测安装状态。
- 信任根失败：暂停远程下载和第三方包，只保留明确标记的本地验证构建。

## 7. 面向用户的实际效果

本轮只改变路线和验收标准，**桌宠界面、菜单、安装路径和运行行为暂时不变**。你得到的是更准确的交付顺序：先确保角色 DLC 安装后真的能播放且冲突不误删，再做状态/租约/事务，最后才开放官方功能选装、远程分发和用户自制 Worker。未来用户安装自制 DLC 时，必须经过完整性/信任、真实加载、停用、卸载和重装验证；不会把 Worker 数量或 Python 模块拆分冒充可拔除交付。
