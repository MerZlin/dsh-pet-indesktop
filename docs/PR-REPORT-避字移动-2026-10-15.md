## 一、核心特性

桌宠自行漫游时不再"踩"在屏幕文字上。每次要移动时，先看一眼屏幕上哪里有字，
如果原随机落点会压住汉字，就把落点换成附近不压字的位置；实在无处可躲（满屏
都是字）就挑压得最少的那一个。

| # | 能力 | 说明 |
|---|---|---|
| 1 | 识别屏幕文字 | Windows 系统 OCR（离线、免费、不联网、截图不落盘），拿到每个词的坐标框 |
| 2 | 看穿自己脚下 | 抓屏时把桌宠窗口排除（`WDA_EXCLUDEFROMCAPTURE`），于是同一张截图里能看到自己背后的真实内容——不用隐藏窗口、不闪、不打断动画 |
| 3 | 落点改道 | 原落点干净就**一步不改**（保留随机漫游的自然感）；脏了才在可达范围内找不压字的落点，就近优先 |
| 4 | 满屏是字时 | 按「先比压住的字数、再比压住的面积、最后比离原落点远近」挑相对最好的 |
| 5 | 后台文字图 | 独立线程刷文字图（默认 3s），移动决策只查表；屏幕内容没变时靠整屏指纹跳过 OCR |
| 6 | 设置页 | 「桌宠」域新增「避字移动」分区：主开关 / 只避开汉字 / 刷新间隔 / 被压住就立刻走开 |
| 7 | 被压住就立刻走开（可选） | 开着时发现自己**此刻**正压着字，不等下一次自选移动，直接打断当前动画走开（默认关） |

**红线 / 不变量**：

- **没数据时绝不改变既有行为**：功能关闭、文字图为空、图已过期（>12s）、几何取不到、
  OCR 不可用——一律把 `(dir_sign, distance, room)` 原样返回、`target_cy=None`，
  窗口继续用它原来的随机纵向漫游。窗口侧唯一改动就是一次钩子调用。
- **随机序列不变**：`wander_target_y` 改为**无条件**求值。它消耗一次随机数，
  若因为避字命中而跳过，后续动画抽取的随机序列会整体错位——测试注入的确定性
  RNG 会静默失效（这条写进了 `window.py` 的注释与架构测试的预算说明）。
- **侧栏 10 个域不变**：侧栏域是外部可见契约（`test_menu_layout.py` /
  `test_settings_interaction_tabs.py` 锁着），避字移动按邻居「边缘探头」的成例
  归到「桌宠」域，不新开侧栏项。
- **纯逻辑层零 Qt**：`pet/text_avoid.py` 顶层不 import Qt（架构测试的红线口径）。

## 三、实现要点

**坐标口径（最容易出错的点）**。三套坐标必须分清：Qt 逻辑像素（`sp.vp` 等）、
抓屏物理像素（原点 = 虚拟桌面左上角）、WordBoundingRect（相对所传位图）。
`CoordMap` 只用一个锚点换算：

```text
logical = anchor + physical / scale,  anchor = vp - WinRect/scale
```

`anchor` 是窗口自身的不变量（逻辑位置与物理矩形同步平移），所以**不需要知道
其它显示器各自的缩放**——本机 1.5 倍缩放、多屏混合 DPI 都不会把别的屏比例算
进来。实机校验：窗口内三个已知位置画中文，OCR 回来的框偏差全部 ≤1 物理像素。

**为什么必须"看穿自己"**。桌宠压在字上时，抓到的画面只有桌宠自己。
`WDA_EXCLUDEFROMCAPTURE` 让窗口照常显示但不进抓屏结果，于是同一张截图里就是
它背后的真实内容。备选方案都更差：隐藏窗口再抓会闪、会打断动画；`PrintWindow`
抓下层窗口在 GPU 加速窗口上经常拿到黑图。实机 A/B/A 比对确认：置位前窗口内
像素 = 窗口自身颜色，置位后 = 背后内容，且自己画的字不再被 OCR 到。

**为什么文字图要缓存**。一次条带 OCR 实测 137–190ms（全屏 911ms），放 GUI
线程会卡动画。改成后台线程刷图（默认 3s）+ 决策时纯查表。另外桌宠已被排除在
抓屏之外，所以**桌宠自己走动不会改变整屏指纹**——静置桌面上每轮只花一次抓屏
（约 50–90ms）加一次缩图，OCR 完全省掉。

**评分为什么是 `(压住的字数, 压住的面积)` 二元组**。只看面积会让"压住一个字但
压得很实"和"掠过三个字"排序反直觉；先比字数（视觉上"压住了几个字"最直观），
同分再比面积。单字判定阈值取
`max(8px², min(15% × 词框面积, 200px²))`——**上界不可省**：OCR 偶尔会把一整段
并成一个大词框，只按比例算的话，桌宠整个身体坐在上面都够不着 15%
（实测 3000×600 的框要压 27 万 px² 才算），"压住了满屏的字"会被误判成干净。

**取舍**：

- *为什么不新开侧栏域*：侧栏 10 个域被两个测试锁为外部契约。先按
  `settings_file_interpret` 成例开了「避字移动」页，5 个契约测试立刻红——
  这不是"测试要改"，而是确实动了对外可见的信息架构。遂撤回，改按邻居
  「边缘探头」的成例（行工厂 + claim 归位）放进「桌宠」域。
- *为什么不打断当前动画*：用户明确选择「只在下一次自选移动时改道」。所以决策
  点只有一处——`_try_move` 建计划时，不做任何运行中的纠偏。
- *为什么钩子返回四元组而不是 `None`*：让窗口侧只有一行、无分支；功能关闭时
  由控制器原样返回入参。

## 四、性能分析

**方法（可复现）**：

```powershell
# 决策与指纹开销（合成 200 词框，条带实测量级：全屏 563 / 条带 137–211）
.\.venv\Scripts\python.exe D:\ComputerUse\_probe\bench_text_avoid.py
# 真实链路（抓屏 + OCR）
.\.venv\Scripts\python.exe D:\ComputerUse\_probe\ocr_chain_probe.py
```

环境：Windows / Python 3.11.9 / PySide6 6.11.2 / Pillow 12.3.0 / winrt 3.2.1；
屏幕 2560×1600 物理、1707×1067 逻辑（1.5 倍缩放）；样本量见下表。

| 指标 | 实测 | 归属 |
|---|---|---|
| 一次决策 `plan_avoid`（200 词框，压字分支） | 优化前 中位 **49.3ms** / 最大 79.7ms；优化后 中位 **8.4ms** / 最大 12.6ms | 新增（GUI 线程，每次自选移动一次） |
| 一次决策（原落点干净，提前返回） | 0.2ms（一次 `text_cost`） | 新增 |
| `text_cost` 单次（200 词框） | 中位 0.17ms | 新增（优化后只在内层小集合上跑） |
| 整屏抓取 + 裁剪条带 | 抓屏 47–88ms（与条带高度无关，位图一次拷出）+ 裁剪 4.9ms | 新增（后台线程） |
| PIL 图 → SoftwareBitmap + OCR | 条带 2560×400：**186ms**；2560×240：**137ms**；全屏 2560×1600：**911ms** | 新增（后台线程） |
| 整屏指纹（2560×1600 缩到 64×64） | 中位 13.4ms | 新增（后台线程） |
| 全屏 OCR 词框数 | 563 个（含汉字 322） | 新增 |

**结论**（逐条）：

1. **稳态开销**：功能**默认关闭**，关闭时窗口侧只有一次函数调用即返回
   （`_text_avoid_move` 读到 `enabled=False` 立刻原样返回），无线程、无定时器、
   无抓屏、无系统调用——与改动前逐字节等价。开启后稳态 = 每 3s 一次抓屏
   （50–90ms，后台线程）+ 一次指纹（13ms）；屏幕内容变了才追加约 137–190ms 的
   OCR。**全部在后台线程**，GUI 线程只承担一次决策（中位 8.4ms，低于本仓库
   自己 150ms 的 GUI 冻结判定线）。
2. **新增路径成本与触发频率**：`_try_move` 是自选移动的建计划点（默认动画链下
   约每 30s 一次）；单次 GUI 线程占用 8.4ms，即 30s 里占 0.03%。
3. **新增的系统调用 / 网络 / 磁盘 / 线程**：新增 1 个 daemon 线程（`pet-text-avoid`，
   仅功能开启时创建、关闭时 `stop()`）、1 个 500ms 的 GUI 定时器（做"该不该
   刷新"判定）、1 个 `SetWindowDisplayAffinity` 调用（状态变化时才调）、每轮
   1 次屏幕抓取。**无网络**：OCR 是系统本地引擎，截图只在内存里、不落盘、
   不外发。无磁盘写入（除日志）。Qt 定时器/线程均按本仓库约定（GUI 线程持有
   Qt 对象，跨线程只走 queued Signal）。
4. **内存与缓存**：文字图是一个 `tuple[TextBox]`，实测条带 137–211 个词框、
   全屏 563 个；`TextIndex` 另存一份索引（词框数 × 约 2 个格子）。整屏位图
   （2560×1600×4B ≈ 16MB）在 worker 线程内即用即弃，与既有 `vision.py` 抓屏
   同量级。**无随时间的单调增长**（每轮覆盖同一个元组字段，无累积容器）。

## 五、实机运行记录

**本机真实环境**（Windows / 屏幕 2560×1600 / 1.5 倍缩放），不是 CI、不是 mock。

### 5.1 前提的现场复现：抓屏默认只看得见桌宠自己

`WDA` 机制先用一个仿桌宠窗口（Qt 无边框 + 半透明 + 置顶，与 `PetWindow` 同类）
做 A/B 双进程实验验证，再在探针里复验：

```text
置位前截图 (525, 435) 像素 = (239, 239, 242)   ← 窗口自己（近白）
SetWindowDisplayAffinity -> True
置位后同点像素 = (45, 56, 87)                  ← 背后的真实内容
排除后窗口矩形内 OCR 到的汉字数 = 34            ← 自己画的字看不见了
```

### 5.2 坐标对齐（三处已知位置，偏差 ≤1 物理像素）

```text
窗口逻辑=320,260 物理=(480, 390, 690, 330) dpr=1.5
CoordMap anchor=(0.0,0.0) scale=1.5
  避字坐标甲: 期望≈(510,447) OCR=(510,446) 偏差=(+0,-1)
  避字坐标乙: 期望≈(510,537) OCR=(510,536) 偏差=(+0,-1)
  避字坐标丙: 期望≈(510,627) OCR=(510,626) 偏差=(+0,-1)
```

### 5.3 用户可见行为：真实屏幕上确实改道到不压字的地方

把窗口摆在一段真实文字上，用**真实 OCR 词框**跑决策，再**真的移动窗口**，
最后用两种口径复核（分开答"几何对不对"和"内容变了没有"）：

```text
条带内词框 180 个（含汉字 87）
当前位置压字 = 20 个 / 5722px²
原随机落点压字 = 13 个 / 4862px²
避字后落点压字 = 0 个 / 0px²  changed=True
横向位移 = +372 逻辑像素，纵向位移 = +0
[强制] 原落点=当前位置(20 个压字) → 落到 0 个 / 0px² changed=True，横向 +600 逻辑像素
实际落位复核：身体框物理=(1470, 435, 1920, 660)
  a) 按决策时词框复算 = 0 个 / 0px²      ← 几何往返精确
  b) 按重新抓取词框复算 = 13 个 / 4753px² ← 这一秒里屏幕内容自己变了
```

(b) 那 13 个压字不是几何错位，而是**决策用的文字图是快照**：探针运行时
DSH 聊天窗口正在流式刷新文字，1 秒后的屏幕已不是决策时的那一屏。同一探针的
另一轮里 (a)(b) 都是 0，正是内容未变的对照。

### 5.3b 在**真实应用进程内**跑起来（离屏实例，不打扰桌面上的桌宠）

本机桌面上本来就有两只桌宠在跑，所以用独立 `APPDATA` + `QT_QPA_PLATFORM=offscreen`
起了第三个实例（`python -m pet`），把 `text_avoid.enabled` 打开跑 3 分半，

```text
                 ——系统截图/录屏将拍不到它，关闭该功能即恢复
（随后 3 分钟内正常切换动画，含 move\螃蟹走路 / move\左转奔跑 / move\漂浮踏步）
```

### 9.2 实现要点：为什么能快两个数量级

第一轮的决策是"在候选网格上逐个试算"：`候选数 × 每候选要比的词框数`。词框 200 个、
格点约 460 个 → 中位 **49ms**（网格索引 + 建索引期过滤后 8.4ms）。

第二轮换了问题结构：**不去试**，而是**一次算清哪些落点会压字**。

给定纵向档位 `cy` 后，某个词框的纵向重叠 `oy` 是常数，而"压住"判据是
`横向重叠 ox × oy ≥ 阈值 t`，等价于 `ox ≥ t/oy`。`ox` 随身体中心平移是一条梯形曲线，
所以 `ox ≥ m` 的解集是**一段连续区间**：

```text
身体中心 cx 落在 [L - W/2 + m,  R + W/2 - m]  →  压住该词框（闭区间）
```

于是每个纵向档位只需把该高度的词框折算成若干区间、求并集，再在空隙里取离原目标
最近的点——`O(n log n)`，**与候选数完全无关**，而且给出的是**精确解**而不是网格近似。

顺带带来一个用户可见的改善：落点由"网格上最近的干净格点"变成"数学上最近的干净点"，
实测同一场景的绕行距离从 **+372px 降到 +55px**（见 9.5）。

**纵向档位优先**是刻意保留的旧语义：按 `_y_candidates` 的顺序（当前高度 → 上/下整档
→ 上/下半档）逐档看，第一档能在 `max_travel` 内解决就用它。第一版实现去掉了这个顺序
（改成在全部档位里挑全局最优），结果出现"为省 13px 横向而先跳 140px 纵向"的反直觉走法，
被 `test_prefers_nearest_clear_spot_over_far_one` 抓住后改回。

**慢路只在一种情况下走**：满屏都是字、一个干净落点都没有（那时"挑压得最少"本来也只能
逐点比）。实测 9.00ms，仍然远低于本仓库 150ms 的 GUI 冻结判定线。

### 9.3 实现要点：立即反应为什么用信号而不是直接调用

控制器不持有窗口的移动接口，只发 `escape_requested`；窗口侧 `_text_avoid_escape()`
自己决定要不要动，守卫四条：**关闭中 / 隐藏暂停 / 用户设了 `no_move` / 已经有移动计划**。
这样"要不要动"这条产品判断留在窗口侧，控制器只管"我发现被压住了"，职责不越界。

落点仍然交给已有的 `_text_avoid_move` 钩子算——立即反应只是**提前触发一次自选移动**，
不新开一条算目标的路径（否则两条路径的落点语义会漂移）。

冷却 6 秒：连续触发会变成抽搐；冷却期内即使仍压着字也不再打断。

3. **系统调用 / 网络 / 磁盘 / 线程 / 内存**：与第一轮完全一致，本轮**没有**新增任何

## 十一、第四轮：落点吸附（准）+ 跑动速度（快）（同日，用户提出）

> 用户："现在跑动的终点选择是不是不够快不够准，加一个跑动速度的选择。"
> **结论：两半都说对了**——决策本身已经精确（0.54ms、区间并集精确解），但
> **落点落地时会再偏**；而赶路速度被步态锁死，长距离确实要走上几十秒。

### 11.1 "不够准"的根因与量化

窗口位移是**帧驱动**的：速度恒等于动画步态、绝不打滑（movement.quantize_move）。
代价是**位移只能落在 ``loops × stride`` 这条离散格子上**。我返回的是"精确干净点"，
落地时因此会再偏最多半个步幅。shenshen 的实测步幅（scale=0.72）：

| 移动动画 | 标定步幅（scale=1.0） | 实际（×0.72） |
|---|---|---|
| 左转奔跑 | 240px | 173px |
| 螃蟹走路 | 220px | 158px |
| 漂浮踏步 | 90px | 65px |

半条就是 30~87 逻辑像素——足够把身体重新压回字上。

**实测（`D:\ComputerUse\_probe\bench_snap_accuracy.py`，400 例随机文字布局，
只统计"精确落点干净且走得到"的情形）**：

| | 落地后又压字 | 比不吸附更差 | 平均多走 |
|---|---|---|---|
| 不吸附（第三轮现状） | 26/400 = **6.5%** | — | — |
| **吸附后（本轮）** | 17/400 = **4.2%** | **0/400 = 0%** | 中位 **+0px** |

修法：新增纯函数 `text_avoid.snap_to_gait()` —— 把落点吸附到
``cur ± n×stride`` 的整圈位置上，并对**吸附后的位置用参考实现复核**，
在 ``(压住的字数, 压住的面积, 与想要的落点的距离)`` 里取最优；
``room`` 夹住不越界，且**候选里至少留一个**（第一版在所有候选都被 room 排除时
退回"未吸附的 want"，等于静默放弃复核——被测试抓到后补上"把候选夹进 [1, n_max]
并把 room 允许的最远整圈也纳入"）。

**剩下的 4.2% 是设计取舍，不是没修好**：那 17 例里"整圈格子上根本没有干净落点"
（干净空隙比步幅还窄）。把搜索圈数从 3 放宽到 6/12/24，干净落地率一模一样
（383/400 = 95.8%，平均落点距原目标 63px 不变）——说明瓶颈是格子本身，不是搜索范围。
要消掉它就得允许最后的零头滑步，那会破坏"绝不打滑"这条既有不变量，故不做。

### 11.2 "不够快"：加"避字跑动速度"

位置由解码帧号驱动 ⇒ **动画多快就走多快**。所以提速的正确做法是提高本次移动动画的
播放速率，而不是去改 duration（那会变成滑步）。项目里已有同款先例：**飞行期动画加速**
（`_stop_physics` 复位回用户速率）。

**第一版做错了，实机才发现**：倍率用 `QTimer.singleShot(0, …)` 在动画**起播之后**施加。
实机抓 ffmpeg 命令行 + 逐拍时间线后查明：**WebM 后端的帧产出速率是 reader 启动时用
`-readrate` 写进命令行的**（抓到 `-readrate 3.0 -stream_loop … 螃蟹走路.webm`），
起播后再调 `set_playback_speed` 只改呈现节拍、**不会有更多帧**——实测 3x 仍按 1x
走完（10.0s，与 1x 的 10.1s 无差别）。

修法：

1. 倍率改成**一次性标记** `_pending_run_boost`，由 `_switch` / `_switch_fallback` 在
   `movie.start()` **之前**取走并叠加到用户速率上（两处各一行）；
2. 一圈时长：仍以 `lib.duration()` 为基准（**不能绕过**——"冷 meta 时 `duration()==0`
   → 不建移动计划"是既有契据，第一版直接读 `clip.duration()` 把它丢了，
   `test_move_sync::test_try_move_skips_when_meta_cold` 当场红：冷素材会按错的总帧数
   瞬移），只在有倍率时把 clip 上残留的速率还原成基础值再按本轮折算（+5 行）；
3. **只作用于"真的为避字改道"的那一次移动**：原落点本来就干净时返回 1.0，普通漫游
   不受影响；下一次 `_switch` 取到 1.0 即复位（有专门用例守着"不漏进下一次普通移动"）。

设置项「避字跑动速度」：1x / 1.25x / 1.5x / 2x / 2.5x / 3x，默认 **1.5x**；
配置键 `text_avoid.run_speed`，归一化区间 [1.0, 3.0]（下限 1.0：不许靠它把桌宠调慢；
上限 3.0：再快动画糊成一团、失去"跑"的可读性）。

**实测（`D:\ComputerUse\_probe\debug_repeat_boost.py`，真实 WebMClip + 真实 PetWindow，
离屏，同一动画"螃蟹走路"、一圈位移 158px）**：

| 跑动倍率 | 起播时 clip 速率 | 实测耗时 |
|---|---|---|
| 1x | 1.00 | **10.1s** |
| 3x | 3.00 | **3.4s** |

三条连续 3x 全部 3.4~3.5s（一轮更早的探针里出现过一次 13.6s 的离群值：那次探针同时
跑着十几个 reader 在争抢解码，复跑不再出现——**高负载下 reader 冷启动可能吃掉收益**，
列入已知限制）。

**顺带的实测观察（未采纳的方向）**：每圈素材里有相当比例是**原地静止**——
左转奔跑 241 帧里只有 118 帧在走（静止 51%）、螃蟹走路 20%、漂浮踏步 8%。
"跳过每圈末尾的静止段"本可再省一截且不依赖解码端，但它要动 `_end_move_or_anim` 的
续圈时机（多圈移动的时序核心），收益与风险不匹配，本轮不做，记录在此备查。

### 11.5 已知限制与后续（第四轮补充）

1. **4.2% 的落地仍会压字**（见 11.1）：整圈格子上确实没有干净落点。消掉它必须允许
   最后零头滑步，与"绝不打滑"冲突，故不做。
2. **跑动速度上限 3x**：再高动画会糊。它同时提高动画与位移，所以"赶路时间 ≈ 原时间 ÷ 倍率"。
3. **高负载下 reader 冷启动会吃掉收益**：倍率靠"启动 reader 时把 `-readrate` 调大"实现，
   若那一刻系统正被十几个 ffmpeg reader 抢占（本机探针里出现过一次 13.6s 的离群值，
   复跑不再出现），这次加速就会打折甚至失效。不是逻辑错误，是解码资源竞争。
4. **多开时同素材共享解码的速率会短暂分叉**：倍率期间该 clip 与发布源的速率不一致，
   `decode_fanout` 会按既有设计回退成本窗本地解码（`SPEED_EPSILON` 那条路），
   移动结束/切动画即复位。飞行期加速本来就走同一条路。
5. **跑动速度不作用于手动拖拽/抛掷**：它只改"避字那一次自主移动"的动画速率。
6. **每圈素材自带静止段**（左转奔跑 51%），所以即使 3x，一次 4 圈的长距离移动仍有可观
   的"原地站着"时间。想再快就得改续圈时机（见 11.2 末尾），本轮不做。

11.5 分钟 8 次逃逸，其中**两对恰好相隔 6 秒**（= `REACT_COOLDOWN_SECONDS`）：冷却一到


三件事合起来就是用户看到的现象：**冷却一到就再逃**（逃逸根本没解决）、
**为了找干净点横跨半个屏**、**偶尔越改越差**。

### 12.2 三处修改

| # | 问题 | 修法 |
|---|---|---|
| 1 | 逃逸之后还是压着字 → 6 秒后再逃，循环 | **白走退避**：逃逸后文字图刷新过、若仍然压着字，记一次"白走"，判定间隔按 2ⁿ 翻倍（6s → 12 → 24 → 48 → **96s 封顶**）；一旦发现当前位置干净立即清零。 |
| 2 | 附近根本没有干净落点也照样走一趟 | **逃逸先确认有地方可去**：新增 `escape_is_worthwhile()`，走与改道**同一条规划路径**（`_plan_at`），只有 `plan.touched == 0`（`max_travel` 内确实找到干净落点）才走；否则原地不动并照样记一次退避。 |
| 3 | 吸附后的落点比原来的随机落点更差 | **改道不许更差**：吸附结果与 `plan.proposed_*` 比 `(压住的字数, 面积)`，更差就**不改道**（保留原落点，也不用跑动速度）。 |

顺带做了一次**内部重构**：把几何准备与 `plan_avoid` 调用抽成 `_plan_at(sp, proposed_cx)`，
`adjust_move`（改道）与 `escape_is_worthwhile`（逃逸判定）共用同一条路径与同一个几何
快照——"能不能去"和"实际怎么去"必须用同一套判据，否则两处会各自漂移。

**语义上的一处刻意区分**（与用户最初的选择并不冲突）：

- **普通漫游改道**：满屏都是字时仍然"挑压得最少的"（这是用户明确选过的行为），
  只是不许比原落点更差；
- **立刻走开（打断动画）**：只认**真的干净**的落点。打断一次动画却只是换个地方
  继续压着字，是纯亏——这正是"乱跑"的来源。

| 新增/更新用例 | 「附近没有干净落点就不许走开」+「连续白走按 2ⁿ 退避、干净即清零」+「吸附后更差就不改道」；两个既有 react 用例按新契约补齐（假宿主提供 `_move_space`）。功能测试 **47 passed**。 |

### 12.4 已知限制与后续（第五轮补充）

1. **退避是"收敛"而不是"解决"**：屏幕一直满字时它仍会每隔最多 96 秒动一次。
   真要彻底安静可以给「立刻走开」再加一个"连续 N 次无解就停到屏幕变化为止"，
   但目前的退避已经把它压到可接受区间，先看实机表现。
2. **逃逸判据用的是精确干净点，不含步态吸附**：吸附那一步需要本次移动动画的步幅，
   而逃逸判定发生在选动画之前。这点残差（实测 4.2%）交给白走退避兜底。
3. **同族桌宠叠加不是 bug**：我一度怀疑"两只桌宠互相遮挡会让 PrintWindow 抓到另一只
   鱼、从而把有字的地方误判为没字"。核对后不成立——底下确实是另一只桌宠时，那块
   **视觉上本来就没有字**，填它的内容是正确的；只是那只走开之后会露出字，属于
   "文字图是快照"的既有局限，由退避与下一次刷新消化。

### 13.4 改用上游 OCR（本轮的主要工作）

上游现在自带一整套屏幕 OCR（`pet/screen_capture/ocr.py`）：**RapidOCR（PP-OCR 模型 +
ONNXRuntime）**，模型随包（`resources/rapidocr_models/`，30.3 MB）、断网可用、**跨平台**、
返回 `TextBlock(text, score, box四角点)` 带 `bounds`。我原先自建的 winrt OCR 是重复建设，
而且把功能锁死在 Windows 上。改法：

- `ocr_available()`：只做"模块可导入 + 模型文件在位"的**静态检查**
  （用上游 `ocr_models.model_problem(resolve_model_dir())`），**不试识别**——起一次进程
  要 3~4 秒，开关是否生效不该付这个代价；
- `read_words_from_image()`：PIL → `QImage`（顶层零 Qt 的契约靠函数内导入维持）→
  `OcrEngine().recognize()` → 每个 `TextBlock.bounds` 转成一个绝对坐标 `TextBox`；
- 上游给的是**行/块级四边形**（不是词级），取外接矩形——比词框粗，方向上是"宁可多避一点"。

**成本实测（同一块 1626×640 真实屏幕条带）**：

| 方案 | 单次成本 |
|---|---|
| 上游 RapidOCR（一次识别 = 一个子进程，每次重新加载模型） | 冷启 **10.6s**，之后 **3.0 / 3.4 / 4.0 / 3.6 秒** |
| 我的 winrt（进程内，仅 Windows） | **125–281 毫秒** |

差 15~30 倍。上游那套是"用完就丢"的进程模型（他们为**手动触发**的截图功能拍板的取舍：
常驻内存归零），套到"3 秒一轮的轮询"上等于**每分钟起 17 个进程、常驻占一个核**——
不能这么用。所以本轮同时改了**节拍**：

| 项 | 旧值 | 新值 | 理由 |
|---|---|---|---|
| 「文字图刷新间隔」默认 | 3 秒 | **30 秒** | 一次识别 3~4 秒；文本布局是慢变量。 |
| 同项可选范围 | 1–60 秒 | **10–300 秒** | 下限 10 秒：再密就是拿一个核换几乎不变的布局。 |
| 文字图保鲜期 | 写死 12 秒 | **`max(60, 3 × 刷新间隔)`** | 保鲜期若短于刷新间隔，每轮刚刷出来的图当场就是"过期"的，功能等于没开。 |

**通路验证**（PIL 画的中文图，避开 Qt offscreen 没字体的坑）：

```text
合成图识别: 3.8s → 3 块
   '避字移动测试'        (123,222)-(377,277)  汉字=True   ← 图内 (23,22) + origin(100,200)
   '桌宠不要压住这一行汉字' (123,301)-(577,358)  汉字=True
   '第三行 English 12345'  (120,377)-(537,444)  汉字=True
```

坐标含 origin 偏移正确、汉字判定正确、`ocr_available()` 为 True。另外验证了"看穿自己脚下"
这条路（PrintWindow + 该 OCR）的连通性。

**坐标口径（这次最容易错的地方，单独立了测试）**：控制器要的是**全局逻辑像素**，

"overlay 全局原点 + sprite 局部" 平移；同时把 `window_physical_rect(overlay)` 交给
`CoordMap`（`anchor = vp − WinRect/scale`），保证物理↔逻辑换算与 legacy 同一套。
另外 `_stable_body_local_rect()` 必须返回**相对 sprite**的身体框（不是相对 overlay），
否则 `target_y` 会整整差一个 sprite 的 y。

## 十五、第八轮：**按需刷新 + 输入缩到"搜索框"**（同日，用户追问"为什么间隔不能变小"）

> 用户问："为什么间隔不能变小，要反复开新进程？"——这一问问出了三件事：我先前的一个
> **错误归因**、一个**真 bug**，以及一个**本该这么做**的结构改正。

### 15.1 先纠正我自己的错误归因：大头是**推理**，不是"反复开进程"

我先前说"一次识别 = 起进程 + 载模型，约 3~4 秒"，暗示进程/模型是主要成本。实测把
三个阶段分开计时（全新进程、真屏幕条带 1626×640）：

| 阶段 | 实测 |
|---|---|
| 解释器启动 + 导入（Qt + 项目模块） | **0.20s** |
| 建 3 个 onnxruntime session + 载入模型权重 | **1.50s**（worker 自报 `loaded ms=1500`） |
| **同一张图的推理**（模型已热，连续 3 次） | **2.9 / 3.1 / 3.4s** |

⇒ **常驻 worker 只能省约 1.7 秒**，剩下每次仍要 ~3 秒纯推理。根因是上游 OCR 刻意只用
**2 个 CPU 线程、关自旋**（他们写明"桌宠是常驻后台程序，识别期间把整机 CPU 打满是
不可接受的代价"）。所以"下限 10 秒"的真正原因是**一次识别约 3 秒 CPU**，而不是进程开销。
（这也说明：单方面把间隔调到 3 秒，等于常驻占满一个核并排队追不上。）

### 15.2 输入面积确实是第二个杠杆（但默认设置下收益有限）

| 输入（同一块屏幕） | 推理 |
|---|---|
| 1626×640 | 2672ms |
| 800×400 | 2187ms |
| 400×200 | 1234ms |
| 200×100 | 891ms |
| 1626×640 但**只做检测**（`use_rec=False`） | **1297ms**（框 31 个、文字 0 条） |

每次调用有约 0.85s 的固定底，所以缩小输入是次线性收益；"只检测"是 2× 但会丢掉文字
内容（只有 `cjk_only=False` 时语义等价）——那要动上游 `ocr.py` 的参数缝（worker 的参数
现在是模块常量），**本轮只在 PR 里作为提案**。

### 15.3 改动一：刷新从"定时轮询"改成"按需 + 最短间隔限流"

识别只在两个**需求点**发起，且都只**发起**（后台线程跑），绝不阻塞 GUI 线程：

1. 要挑落点时（`_plan_at` 发现手里没有可用文字图 → 发起，本次原样返回，下一轮就有图）；
2. 「被压住就立刻走开」想判定而没有图时（`_maybe_react` → 发起）。

`refresh_seconds` 的语义随之从"轮询周期"变成"**最短刷新间隔**（限流）"：

| 项 | 旧 | 新 |
|---|---|---|
| 语义 | 每 N 秒无条件刷一次 | 两次识别之间的最短间隔（按需触发） |
| 默认 | 30 秒 | **10 秒**（按需之后小一点也不费 CPU） |
| 范围 | 10–300 秒 | **5–300 秒** |
| 文字图保鲜期 | `max(60, 3×间隔)` | `max(180, 6×间隔)`——按需之后图的年龄跟着**决策节奏**走（桌宠可能安静几分钟才动），按几十秒判过期会让功能永远不生效 |

效果：识别次数从"每 `refresh_seconds` 一次"降到"**每次移动决策一次**"（桌宠一次移动
20~60 秒），空闲时**一次都不刷**（有专门用例 `test_idle_tick_does_not_refresh_on_its_own`
把定时轮询钉在门外）。

### 15.4 改动二：**OCR 条带 = 规划搜索框**（顺带修掉一个正确性 bug）

在此之前这两者并不一致：条带按**整屏宽**铺、纵向只盖"身体上下各一个 `y_margin`"，
而规划器的**纵向搜索范围是整屏**——于是"往上一大截"的候选落在**没 OCR 过的区域**里，
代价读成 0（看起来干净），桌宠会往那儿走。

现在两者**同源**（新 `_geometry_box()` 单一来源，`_current_band` 与 `_plan_at` 都从它取）：

- 横向搜索框 = `当前位置 ± max_travel`（夹到屏内）；
- 纵向搜索框 = `身体 ± y_margin`（夹到上下安全边距）；
- **条带就是这个框**（下限只放大条带、不放大搜索框，方向是安全的那一侧：条带 ⊇ 搜索框）；
- 规则因此可陈述：**看不到的地方不许选**。

顺带把 `_plan_at` 里重复算的几何删掉了（原来两处各算一遍，正是漂移的来源）。

**实测（真机、dpr=1.5、2560×1528）**：

```text
旧条带（整屏宽）   2560 x 711 = 1.82 Mpx
新条带（=搜索框）  2227 x 711 = 1.58 Mpx   → 1.15× 更小
新条带位置         (332,542)，与 sprite 位置自洽（身体顶 751 − y_margin 210 = 542）
```

默认设置（`max_travel=700`/`y_margin=140`）下只有 1.15×——横向范围由 `max_travel` 主导；
但**成本从此随这两个设置缩放**（有用例钉住"调小它们 → 条带同时变小"）。

### 15.5 15.4 顺带暴露出**坐标错位**的真 bug（单元测试全绿也漏掉了）

做 15.4 的真机测量时，新条带的坐标是 **`(-820, -146)`**——跑到屏幕外了。根因是
`CoordMap` 的锚契约：`anchor = 逻辑位置 − 物理原点/缩放`，需要"**同一个**窗口的逻辑
位置与物理矩形"配对；而 sprite 不是窗口，适配器第一版把 **overlay 的物理矩形**配上了
**sprite 的逻辑位置**，于是 anchor 被算成 sprite 自己的逻辑位置——**身体框与条带整体
偏了一个 sprite 的距离**（实测条带几乎全在屏幕外、身体框算在左上角）。

后果不只是条带位置难看：代价函数会拿"错位的身体框"去比对绝对物理坐标的文字框，
等于在**错的地方**判断压不压字。

修法：控制器新增可选宿主钩子 `_coord_physical_rect()`——由宿主给出**与 `_virtual_pos()`
配对**的物理原点（sprite 世界自己换算：`overlay_px + (sprite_logical − overlay_logical)
× dpr`），拿不到才回落到按 HWND 查 Win32 矩形（legacy 那条路不变）。修后实测条带
`(332,542)` ✓ 自洽。

**为什么单元测试没发现**：假几何里 overlay 在原点、dpr=1，偏移恰好只体现在绝对坐标上，
而当时没有一条用例断言"身体框的物理位置 == 逻辑位置 × dpr"。已补回归守卫
`test_host_physical_origin_pairs_with_virtual_pos`。

### 15.8 全量跑出来的第三个真 bug：**ctypes argtypes 跨模块串台**（同样静默）

全量套件里 pytest 报了一条"未捕获异常"，来源是我写的 `topmost_window_under` 回调：

```text
PytestUnraisableExceptionWarning: Exception ignored on calling ctypes callback function
  File "pet/platform_win.py", line 481, in _cb
    u32.GetWindowRect(hwnd, ctypes.byref(r))
ctypes.ArgumentError: argument 2: TypeError: expected LP_RECT instance
                                     instead of pointer to _WinRect
```

根因：**`ctypes.windll.user32` 是进程级共享的函数对象**——谁设了 `argtypes` 就定死了
之后所有调用者的签名。本项目里两处在抢它：

| 位置 | 设为 |
|---|---|
| `pet/vision.py:105` | `[HWND, POINTER(wintypes.RECT)]` |
| `pet/platform_win.py:435`（我加的） | `[HWND, POINTER(_WinRect)]` |

两者布局等价但是**不同类型**，后设的那一方会让另一方的调用点直接 `ArgumentError`。
更糟的是它**静默**：

- `window_physical_rect` 有 `except → return None` ⇒ 几何取不到 ⇒ **避字移动静默不生效**；
- `EnumWindows` 回调里的异常被 ctypes 自己吞掉 ⇒ 表现成"拿不到底下那个窗口"。

**修法（只动我加的那两个函数，不碰上游代码）**：本模块自己要用的调用一律走**私有绑定**
——`ctypes.WinDLL('user32')` 每次实例化都是新对象，不参与 `windll` 的共享缓存，因此
它的 `argtypes` 与别处互不干扰；`window_physical_rect` 也不再修改共享签名（只在测试注入
替身时使用注入对象）。

顺带修掉同一族的第二处：`_is_cloaked`（也是我加的）**没有声明 argtypes**，64 位下 HWND
会被默认按 int32 传（本项目在别处明确写过这个坑），改走私有 `dwmapi` 绑定并显式声明签名。

复验（把共享签名改成 vision 那套敌意签名，其余不变）：

```text
topmost_window_under → 1840014
window_physical_rect → (0, 0, 1707, 1067)
_is_cloaked          → False
```

回归守卫：`tests/test_platform_win_private_bindings.py`（敌意签名下两个函数必须仍可用 +
注入替身优先且不改共享 argtypes）。

### 15.9 第九轮：给上游 OCR 加"只检测"档（`use_rec`），并踩到两个宿主侧的坑

§15.2 量出"同尺寸只做检测是 2×"之后，维护者/用户点头做这一档。做法是**最小侵入**的：
不改 `recognize()` 的默认行为，而是用它**已有的命令行**做开关。

| 位置 | 改动 |
|---|---|
| `pet/screen_capture/ocr.py` | 新增 `OCR_NO_REC_FLAG = "--ocr-no-rec"`；`worker_command(use_rec=True)` 在 `use_rec=False` 时把它附在命令行末尾（**默认逐字节不变**） |
| `pet/screen_capture/ocr_worker.py` | `load_engine(use_rec=...)` 合并 `{"Global.use_rec": False}`；`to_blocks(result, use_rec=...)` 在只检测时不要求文字、把框原样发出（`text=""`）；`run(..., use_rec=...)`；`main()` 解析该开关（其余参数一律忽略，冻结态的 `--ocr-worker` 不需要再解析） |
| `pet/text_avoid.py` | `_ocr_engine(use_rec=True)` 按档缓存两个引擎（用 `OcrEngine(command=lambda: worker_command(use_rec=False))` 这个**既有注入缝**）；`read_words_from_image(..., need_text=True)` / `read_under_pet(..., need_text=True)` |
| `pet/text_avoid_controller.py` | `_refresh_once` 里 `need_text = bool(cfg["cjk_only"])` |

**关键不变量**：`need_text == cjk_only`。只检测的结果里**没有文字**，如果还按"只避汉字"
过滤，整张图会被判成"哪都没有字"——功能看起来像没开。所以两者必须配对（有参数化用例钉住）。

**worker 端刻意不 import `ocr.py`**（那会把 Qt 拉进这个只为识别而生的进程），因此
`--ocr-no-rec` 这个字面量在两侧各写一份，并有一条用例比对两处相等。

#### 实机验证（真子进程）与两个宿主侧的坑

第一次用真子进程验就炸了，而且是**两个我自己没预料到的坑**——都不是"跑通了"能发现的：

1. **ndarray 的真值判断**：`to_blocks` 里我写了 `if not boxes:`，而 rapidocr 的
   `.boxes` 是 **ndarray**，多元素数组做真值判断直接抛
   `The truth value of an array with more than one element is ambiguous`
   （上游原有那几行特意用 `is None` / `len(...)` 正是这个原因）。改成 `is None or len(...) == 0`。
2. **宿主侧会把空文字的块丢掉**：worker 明明发出了框（手动起进程看 stdout 确认过），
   但 `OcrEngine.recognize()` 返回 0 块——因为 `blocks_from_payload` 有
   `text = ...; if not text: continue`。对展示类调用方丢空块是对的（它们是噪声），
   所以**没有改这个默认**，而是显式开口子：
   `blocks_from_payload(raw, keep_empty_text=False)` +
   `OcrEngine.recognize(image, keep_empty_text=False)`，只检测档传 `True`。

修完之后的实测（同一张 1626×640，真子进程；worker 侧 stage 记录确认
`"use_rec": false` 且 stdout 里"有框没文字"）：

```text
文字较多的条带：检测+识别 3.8s / 60 块   →   只检测 2.4s / 60 块（文字全空）
文字很少的条带：检测+识别 2.4s /  1 块   →   只检测 2.4s /  2 块
```

即 **省掉的是"识别模型那一半推理"，收益随框数走**：框多时约 1.6~2×，框少时几乎没差
（此时耗时被固定成本——起进程 + 载模型 ~2.3s——吃掉了）。这一点必须说清楚，
否则"开了这档却没快"会被当成 bug。

顺带一个**行为差异**（不是 bug，写下来备用）：只检测时框通常**更多**（上例 2 vs 1）——
识别阶段会合并/丢弃一些框，而检测阶段只知道"这里有一块文字"。方向是"宁可多避一点"，
与本功能的口味一致。

#### 测试（第九轮）

## 十六、第十轮：**实机 bug —— 文字图冻结**（次日用户现场报告："没字也跑开，还跑到有字的地方"）

> 用户报告：**"好像没有字她也跑开，还跑到有字的地方了。"**
> 这一条是我第八轮"改成按需刷新"时留下的真缺陷，先看实机日志再动手。

### 16.1 日志把病灶指出来了

`%APPDATA%\dsh-pet-standalone\pet-21604.log`（运行中的那只，pid 21604）：

三个特征一凑，病灶就清楚了：

1. **"当前位置压 3 字/5957px²" 五次一字不差** ⇒ 判断一直基于**同一张文字图**；
2. **每 6.000 秒一次**（`REACT_COOLDOWN_SECONDS`）⇒ 冷却一到就再来一趟；
3. 每趟都把落点改成"改后压 0 字"的**518px**外 ⇒ 在她那张旧图里那儿是干净的。

也就是说：**她在 A/B 两点之间按 6 秒周期来回跑**——A 在旧图里"压着字"（幻影），
而她选的 B 是照旧图算的，实际那里**早就有字了**。这同时解释了用户说的两句话：
"没字也跑开"（A 处其实没字）＋"跑到有字的地方"（B 处其实有字）。

把这个循环按时间顺序摊开，还能看到它的**起止条件**（同一只进程，21:42–21:51）：

```text
21:45:01  5字/27551px²   ← 新一轮开始
21:45:07  5字/27551px²   （间隔 6s，代价一字不差）
21:45:13  5字/27551px²
   …（连续 20 次，全部 6 秒一次、代价完全相同）
21:46:55  5字/27551px²
21:48:17  2字/6497px²    ← 76 秒后：图终于被换掉了，循环中断
…
21:50:42  1字/4306px²    ← 又一轮，连续 5 次
21:51:06  1字/4306px²
```

**串与串之间隔 25~100 秒——正好是那个 120 秒低频兜底刷新把图换掉的时刻。**
也就是说：那个 6 秒乱跑循环**只会被"图终于刷新"打断**，最长一次连续 20 次
（两分钟里她每 6 秒冲一次）。这条把 16.2 的因果彻底钉死了。

### 16.2 根因：按需刷新只在"完全没有图"时才发起

第八轮我把定时轮询改成按需，触发条件写成了**"手里没有可用文字图"**：

- `_plan_at`：`if not boxes: self._request_refresh()`；
- `_maybe_react`：`cost is None` 时才发起。

于是**只要图还没过期就永远不刷新**。而保鲜期是 `max(360, 6×刷新间隔)` —— 最长 6 分钟
**一张图不变**，中间所有决策与判定都基于同一份快照 ⇒ 幻影文字 + 落点判断失真。

**第二层放大**：退避只在 `_boxes_at > _escaped_at`（逃逸后图刷新过）时才记失败——
图永不刷新 ⇒ **退避永不生效** ⇒ 那个 6 秒周期雷打不动（用户看到的"一直在乱跑"）。

### 16.3 修法（两处，都在控制器里）

| # | 改动 | 为什么 |
|---|---|---|
| ① | **每次需求点都发起刷新**（`_plan_at` 与 `_maybe_react` 各一处），限流交给 `_request_refresh` 已有的"最短间隔 + 正在刷不重复发起" | "按需"的正确含义是**每次有需求都问一次**，由限流决定真刷几次；写成"没图才刷"等于把"图会不会更新"交给了过期时间，最长 6 分钟不更新 |
| ② | **同一张文字图只逃逸一次**：`_escaped_generation == _map_generation` 时直接返回，等拿到新图再判"上一趟有没有用" | 拿同一份数据反复做同一个决定，结果必然是 A→B→A→B；这是用户看到的"来回乱跑"的直接机制 |

第 ② 条要配一个**安全阀**，否则会引入新的失败模式：万一刷新一直在失败（抓屏/识别报错），
文字图代次永远不会推进，逃逸就会被无限期压住——她被钉在字上一动不动。
所以图超过 `max(30, 2×最短间隔)` 没更新时**放行**：宁可偶尔多跑一趟，也不要卡死。
（这是我在提交前自查出来的：一个"防乱跑"的规则如果不设出口，就会变成"防动弹"。）

第 ② 条顺带把"有没有用"的判据改准了：**换过图之后**比较"逃逸前压几个字"与"现在压几个字"
（`cost[0] >= _escaped_count` 才算白走），不再依赖时间戳比较。为此引入**文字图代次**
`_map_generation`（每拿到一张新图 +1，在 `_on_words_ready` 里推进）——比时间戳直白，
也不会被"测试里用 inf 表示新鲜"这类取值干扰。

副作用（要写下来）：开了「被压住就立刻走开」时，这一档现在**按最短间隔持续刷新**
（用户配置 10 秒 ≈ 每分钟 6 次识别）。这是"持续盯着此刻压不压字"的应有代价；
没开这一档时不走这条路径，也就不会空转刷新（仍有那条按需触发点）。

### 16.4 测试（第十轮）

`tests/test_text_avoid_controller.py` **+5 例**：

- `test_a_decision_asks_for_a_refresh_even_when_the_map_is_usable` —— **本次 bug 的核心回归守卫**：图可用也必须发起刷新；
- `test_the_react_watch_keeps_the_map_fresh` —— 判定那一档同样每拍都要发起；
- `test_only_one_escape_per_text_map` —— 冷却过去但图没换代 → 不许再逃逸；
- `test_escape_backoff_judges_by_whether_the_escape_helped` —— 换过图后"没改善"才记白走，"干净了"清零；
- `test_only_one_escape_per_text_map` 里还钉了**安全阀**：图太久没更新时必须放行；
- `test_the_requested_refresh_actually_replaces_the_map` —— **闭环**：`_request_refresh()` → `_refresh_once()` → `_on_words_ready()` 必须真的换图并推进代次（否则"一张图只逃逸一次"永远解不开）。

全量 `pytest -q`：**7587 passed / 18 skipped / 1 failed**。唯一那条失败仍是
`test_flight_frame_pacing::test_flight_speed_writes_do_not_starve_frame_delivery`
（抛物运动 2500px/s 的**计时**用例；本轮全量 24 分 07 秒，平时 14~18 分钟）。
它单独复跑 4 次全过（其中一次空载也跑出 16.26s vs 平时 2.6s——本身就抖），
而且**该测试文件里没有任何避字相关符号**（`text_avoid` / `move_anim_speed` /
`run_boost` / `SpriteTextAvoid` 全无），判定为环境负载导致的抖动，与本改动无关。

### 16.5 教训

**"按需"不能退化成"只在缺失时才做"。** 我把"按需"理解成"没数据才去取"，结果是把
"数据会不会更新"整个交给了过期时间（最长 6 分钟）。按需的正确形态是
**"每次有需求都问一次，由限流决定实际频率"**——需求点该问就问，别自己在需求点做缓存决策。

第二个教训：**退避/计数这类自适应机制，不能挂在"另一个机制有没有发生"上**
（我挂在了"图刷新过没有"上），否则那个机制一旦不工作，退避就跟着一起失效——
两个独立的保障同时哑掉，用户看到的就是"一直在乱跑"。

### 18.1 这轮的教训：**「上游一直在动」是常态，不是意外**

两小时内两次 rebase（16 个提交 → 1 个 113 文件的大提交），说明这个项目的合并节奏很快。

1. **把 PR 做小**（本 PR 29 文件已属偏大），免得每次 rebase 都要重解一遍；
