# Phase 4：屏幕理解可拔除样板与本地安装事务

> 修订：2026-09-29。**官方选装必做；平台查询、独立视觉配置/确认迁移、贡献以及 host/自包含 Worker 四个切片已有自动化基线。Windows 独立验证产物通过；应用内安装、卸载、跨进程安装状态和正式发布仍待实施。**不把验证版显式加载等同于完整用户交付闭环。

## 1. Phase 4A：审计后确定最小接口，再迁移

样板为屏幕理解，包含自动识屏、手动“看看屏幕”、专属策略/UI/配置、adapter、截图/变化检测/视觉请求；现有 fallback 也必须审计归属。独立交付后 Worker 有限重启耗尽即暂停功能，不回 Core 执行截图或网络；当前 3B 进程内回滚继续保留，但与 Worker 一样只使用独立视觉配置。不得只把 Worker 移走，仍把整套功能、依赖和入口编进 Core。

已形成 [屏幕理解交付边界只读审计](PHASE4A-SCREEN-DELIVERY-AUDIT.md)：核对 Core 共享的窗口/光标查询、聊天配置与凭据依赖、菜单/设置注册、数据与卸载责任，以及已有构建 TOC 的来源。事实、建议和待验证事项分列；该审计阶段未搬代码、重建或固定包格式/安装目录，也没有最小 Core 缺包证据。

随后形成 [Phase 4A 最小拆包设计](PHASE4A-SCREEN-PACKAGE-DESIGN.md)：确定纯平台查询、独立视觉配置/凭据、贡献生命周期、可选聊天服务以及自包含 Worker 的五组接口。两包均启用时保留完整文字同步和后续追问；无 Chat 窗口也可保存，生成中跳过，不排队补发。手动同步发起窗口，共享自动按现有明确目标分别同步；不向所有插件广播。

已确定设计与待实现证据分开：

1. 代码、资源、依赖、import 和 PyInstaller 产物归属清单，区分通用宿主和功能专属部分。
2. 暂定 `official.screen-understanding`；`VerifiedFeatureDescriptor` 定位固定 host factory 和 Worker，不表示已安装。执行前验证发布者签名、路径、文件哈希及兼容性，开发未签名必须显式开启；第四步已使用 cryptography/Ed25519 与封闭摘要清单，验证版仅信任隔离测试公钥，资源 `ContentManager` 不变成任意代码加载器。
3. 首包采用自包含 Worker，接受并测量初期依赖重复；GUI host 随包交付，使用 Core 的 Qt 与公开端口。host/Worker 同版激活；Worker 不借用 Core 安装目录的依赖，须实测子进程 DLL 搜索边界。
4. 自动/手动视觉旧行为分别解析，经确认迁入独立 profile/凭据，之后不跟随聊天变化；备份不含明文 Key。Phase 4B 才在现有应用数据根下引入权威安装状态及跨进程版本占用；当前使用进程内版本句柄，保留原配置/数据路径，不新建 state.json。
5. 最小 Core 构建与 import 清单证据：不携带屏幕理解专属代码/资源/依赖仍能离线启动和基础交互；共用依赖留在何处须明确理由。
6. 菜单/设置/搜索/快捷键按 owner 注册撤销；无包无入口，设置无截图/网络副作用。AI 包通过受限外部问答服务负责保存/会话，Core 只做发现授权与路由，不承接聊天业务。

按“平台查询 → 独立配置与确认迁移 → 贡献/聊天服务 → host 迁移与自包含构建 → 无识屏 Core、无聊天识屏的真实产物验证”推进。[首步平台查询](../PR-REPORT-DESKTOP-QUERY-2026-09-27.md)及[第二步独立视觉配置](../PR-REPORT-VISION-CONFIG-2026-09-27.md)已经实现并通过自动化：基础查询不再导入识屏，识屏设置与请求链不再依赖聊天开关、Provider 或 Key。迁移需预览确认，普通配置不存密钥；真实 keyring/新 UI 用户操作尚待验收。[第三步菜单与设置贡献](../PR-REPORT-SCREEN-CONTRIBUTIONS-2026-09-28.md)已实现 owner 注册/撤销、执行授权和安全草稿管理，最终回归结果见报告；未新增托盘项、整包开关或安装状态。[第四步 host 与独立构建](../PR-REPORT-SCREEN-HOST-BUILD-2026-09-29.md)已实现受限端口、chat.external-turn/v1、单一功能源码和 Ed25519 目录加载；两种无识屏 Core 与独立 Worker 的 10 项真实冻结场景通过。现有默认构建保留，尚不能在应用内安装/卸载；下一步是 Phase 4B 的权威状态与安装事务，不继续用拆分数量代替交付。可并行准备 AI 对话审计，不同时启动第二场大重写。

## 2. Phase 4B：交付第一个完整样板

已确认的下一步合同见 [Phase 4B 本地管理设计](PHASE4B-LOCAL-MANAGEMENT-DESIGN.md)，以同一应用数据根统一管理、占用时自然退出为边界；按唯一状态、跨进程租约、事务恢复、管理 UI、两种冻结产物端到端验收依次推进。**当前仅计划与交接落盘，尚无 Phase 4B 实现结果。**

依赖 4A 的信任与产物方案确定，完成：本地安装 → 启用 → 入口注册与使用 → 停用 → 应用内卸载 → 重装恢复偏好 → 升级/失败回滚。

- 最小扩展管理属于 Core 必做宿主：安装状态、原因诊断、启用/停用、配置、卸载、版本与回滚入口。它不等待 catalog、联网市场或第三方 SDK。
- 未安装不出现专属菜单、设置、搜索和快捷键；设置页面打开不启动截图或网络。
- 默认保留用户数据；停任务/Worker、撤销贡献并协调全部实例后再移除包文件，文件占用则显示待重启完成卸载。
- 屏幕 Worker 故障耗尽后暂停并提供重试/版本回滚，不回 Core 执行；卸载或停用整个包后禁止自动和手动识屏。只关闭自动开关仍允许手动“看看屏幕”。
- 目录/ZIP 是本地来源，代码执行前仍须验证可信来源、完整性与兼容性；哈希不等于发布者身份。

统一事务以 [安装与更新协议](PLUGIN-UPDATE-PROTOCOL.md) 为准，UI 状态以 [API 合同](../plugin-phase-01-foundation/PLUGIN-API-CONTRACT.md) 为准。

## 3. 与其他阶段的关系

- Phase 1 角色安装事务继续使用并回归，不重复实现，不把资源 fallback 当成功能卸载后恢复隐藏实现。
- Phase 3C 的其余 Worker 评估可并行，不要求全部先进程化。
- Phase 5A 将同一闭环接入 Setup、ZIP/便携；5B 首先推广 AI 对话与文件理解，再推进 Agent 与其余官方领域。
- 远程 catalog、镜像和自动检查按实际需求接入；第三方 SDK、Workshop 仍条件化。
- Core 更新沿用现有 updater，本阶段不重构其协议；后续集成必须保证不重装用户已卸载的功能。

## 4. 出口与回滚

硬出口是实际产物与用户操作证据，不是代码文件数：最小 Core 无包可用、安装后入口可用、停用无执行、卸载无专属文件/入口、重装恢复配置。还要测试依赖、权限、离线、多实例、故障、升级和回滚，测量 Core/功能包实际大小与启动/RSS 成本。

4A 未通过不得对外发布可执行包；4B 失败保留最小 Core 与 Phase 1 内容安装，暂停功能包激活，不通过恢复 Core 隐藏实现绕过问题。已安装授权功能可回滚到上个可用版本，用户数据按 [迁移合同](../plugin-phase-01-foundation/PLUGIN-MIGRATION-v4-to-v5.md) 恢复。

## 5. 给使用者的效果说明

你会第一次能“不装识屏也使用桌宠”，以后在桌宠的扩展管理里导入官方本地包，自动和手动识屏入口才出现。包里包含专属 UI、策略、adapter、Worker 和所需依赖；Core 与 Worker 仍通过本机管道连接。卸载会停后台、撤销入口、移除包，默认留下偏好。

单装屏幕理解也能配置视觉服务；单装 AI 也能聊天；两者启用时同步分析文字并继续聊，卸掉任一包不影响另一个的独立能力。角色包与可执行包分开，屏幕包的相对布局、自包含 Worker 和临时凭据边界见最小设计，便携布局留给 5A。当前还没有安装卸载体验，不能把设计目录当作复制即用说明；用户只确认手动识屏，自动及托盘退出仍未验收，并非判定自动功能故障。
