## 1. 目标、事实与不做的事情

必须同时满足：**无识屏包的 Core 可运行；无聊天包的识屏可配置和使用；两包启用时可同步识屏文字并继续聊天。**运行进程独立、配置独立和物理可拔除分别验收，不能相互替代。

| 当前事实与证据 | 本设计据此保留或修正的边界 |
|---|---|
| [app.py](../../pet/app.py) `sync_look_to_chat()` 现为兼容委托；[聊天接收方](../../pet/chat/external_turns.py) 负责会话选择、保存及刷新，窗口未打开也可保存 | 聊天包拥有持久化服务；不以打开 Chat QWidget 为联动前提 |
| [chat/widgets.py](../../pet/chat/widgets.py) `append_look_sync()`：生成中不插入，否则追加完整问答并刷新可见界面 | 保留忙碌拒绝与完整文字，不新增排队、补发或额外模型请求 |
| [multi_window_shared.py](../../pet/multi_window_shared.py) `on_look_synced()`：共享自动识屏同步到各窗的独立会话 | 保留明确的多目标路由；手动结果仍只回到发起窗口 |

## 2. 交付所有权与运行位置

| 所有者 | 包含内容 | 不应包含 |
|---|---|---|
| Core / 通用契约 | 窗口基础行为、纯平台查询、配置/安全存储宿主、授权、贡献与服务路由、Worker Supervisor；安装管理留给 Phase 4B | 截图、视觉 Provider 业务、聊天会话选择与持久化、识屏专属策略/UI |
| 屏幕理解 host（GUI 主进程） | 自动/手动策略、独立视觉设置页、命令、受限状态适配、请求 generation/额度/记忆、气泡与聊天同步适配 | Core 私有对象、Chat UI/SessionStore 直接引用、故障时在 Core 隐藏执行截图/网络 |
| 屏幕理解 Worker（独立进程） | 前台查询后端副本、截图/JPEG/dHash、视觉请求、单帧内存/TTL、取消与心跳、自带运行依赖 | Qt GUI、keyring、全局配置、聊天会话服务、持久截图或密钥 |
| AI 对话包 | Chat UI、Provider/会话与文件理解业务、追加外部问答服务、记录刷新与后续上下文 | 自动获得截图权限、直接连接识屏 Worker、要求识屏包存在 |

“Core 决定是否允许执行”指安装状态、权限与基础状态权威；dwell、白名单、额度等**识屏专属策略随功能 host 交付**，不是永久留在 Core。策略仍在 GUI 主进程不等于它属于 Core 安装包。

```text
Core 通用宿主（状态 / 端口 / 贡献 / 定向服务路由 / Supervisor）
  ├─ 屏幕理解 host ── QProcess + stdin/stdout JSONL ── 自包含识屏 Worker
  └─ AI 对话 host   ←── 受授权的追加文字问答服务 ──── 屏幕理解 host
```

下列合同是内部官方边界，不是第三方稳定 SDK。查询、独立配置/凭据、贡献、定向文字服务及 `FeatureHostContext` 已实现；官方包验证与独立构建已通过 Windows 自动化。持久安装状态、多进程安装租约、应用内卸载及正式信任锚尚待后续实施。

## 3. 接口一：DesktopQueryPort 与受限状态

### 3.1 最小查询合同

| 操作 | 成功值 | 非成功状态 |
|---|---|---|
| `foreground_window()` | `ForegroundInfo(hwnd, pid, process_name, title, rect)`；`rect=(x, y, width, height)` 保留现有坐标语义 | `no_window`、`unsupported`、`error` |
| `cursor_state()` | `showing`、`hidden`、`suppressed` | `unknown`、`unsupported`、`error` |
| `idle_time()` | 非负空闲秒数 | `unsupported`、`error`，不把不支持当成已空闲 |

结果只含不可变/可序列化数据和安全原因码，不返回 ctypes 句柄所有权、Qt 对象或原始异常。内部系统句柄由后端关闭。窗口标题仅作已授权业务输入，不进入通用诊断；没有有效窗口是正常结果，不抢焦点、不重试到无限。

- 纯平台后端只依赖必要平台 API，不导入 Pillow、截图、模型配置、聊天或网络。Worker 将同一后端源码作为**自己的构建输入**，不借 Core 安装目录/PYTHONPATH 找依赖。
- Core 全屏/光标行为继续在本地查询，不为基础桌宠启动识屏 Worker。Worker 请求沿用 `observe_foreground` 等 `pet-worker/v1` 操作，查询 DTO 不另造传输协议。
- 旧 `vision.foreground_window_info()`、光标/idle 入口在迁移期通过兼容适配维持返回语义；现有非 Windows 的 `None`/空闲 `0` 不直接套成新 API 的成功结果。Core 调用方迁完后，Core 包不再因兼容 facade 导入识屏实现。
- 截图、编码、dHash 仍归识屏 Worker；前台观察不等于截图授权，截图前仍验证目标窗口快照与 generation。

### 3.2 功能策略的窗口状态（第四步已实现）

[FeatureHostContext / FeatureWindowPorts](../../pet/feature_ports.py) 按目标窗口绑定，`snapshot()` 返回不可变 `FeatureWindowState`：窗口、实例、角色、名称、可见性、交互和穿透状态；Agent 忙碌单独查询。气泡、等待提示、文字服务、授权及生命周期均为窄回调，不返回 `PetWindow`、`PetApp`、`AppShell` 或 `Config.data`。

配置命名空间、旧字段偏好、限定数据文件及事务状态分别通过端口访问，保持原路径、修订检测和保存语义；设置组件也不接收全局 Config。Core 适配器可读取内部字段，但不把对象传给 host。这是工程/授权边界，不是恶意 Python 的安全沙箱。

验证先用真实 ctypes 结构的确定性系统边界测试；真实桌面探针另行显式执行，不用“当时恰好没有前台窗口”让默认测试失败。平台不支持时明确限制，不以 Windows 通过推断三平台已实现。

### 3.3 首个切片的已实现状态（2026-09-27）

- [desktop_query.py](../../pet/desktop_query.py) 提供 stdlib-only 查询后端、不可变 `QueryResult`/`ForegroundInfo`、Windows 查询与非 Windows `unsupported`。导入不查询系统、不启动线程、不加载 Qt/Pillow/聊天/识屏。
- [vision.py](../../pet/vision.py) 的旧前台、光标、idle、矩形与应用描述入口委托后端；旧字典 `process` 字段、大写光标状态、失败默认值以及 `user32` 注入保留。截图、模型及网络逻辑不动。
- 基础全屏、单窗口光标、共享多窗口监视和设置白名单查询已改用通用模块；不增加缓存、重试、轮询或系统查询次数。设置结构、文案及配置不变。
- 全新子进程阻断 `pet.vision`，分别运行普通/共享模式的真实 `QApplication`、`PetWindow`、监视线程与事件循环，仅替换 WinAPI 边界，验证查询发生、信号到达、零 Worker 启动及正常清理。这不是完整 `PetApp.start()` 或最小 Core 安装包的证明。
- 专项、全量、类型、静态检查、真实前台探针及有界性能见[本切片实施报告](../PR-REPORT-DESKTOP-QUERY-2026-09-27.md)。本步未重建，非 Windows 原生查询仍未实现；配置、贡献、构建与安装卸载继续按后续步骤验收。

## 4. 接口二：独立视觉配置与 CredentialVaultPort

### 4.1 配置所有权

`VisionProfile` 归屏幕理解包，包含自己的 `profile_id`、端点/协议类型、模型、超时/代理策略、视觉提示词及 `credential_ref` 等必要字段；不沿用整个 `ChatProviderConfig` 作为交付依赖。网络行为保留既有视觉代理/TLS语义，不借拆包改用歌词的直连策略。

`VisionSettings` 归每实例插件命名空间，包含 schema、profiles、自动与手动的 profile 绑定，以及识屏自身偏好。Core 只存/迁移命名空间与执行授权，不解释视觉模型业务。自动/手动有效设置、提示词和凭据等确实一致时才可共用 profile；不因为端点或名称相同就合并。

迁移后的视觉端点、模型、提示词与凭据独立：**后续切换聊天 Provider 或删除聊天包都不会改变视觉配置**。无聊天包也可编辑、验证格式并保存视觉设置；保存/打开页面不发请求，任何联网试用都须明确命令和授权。

### 4.2 最小安全存储端口

`CredentialVaultPort` 由宿主绑定 `(owner, instance_id, profile_id)`，功能不能传任意 owner 访问别人的秘密。最小操作为安全写入/替换、是否存在、按单次请求取得短期使用权以及经单独确认的删除；返回普通配置的只是 opaque `credential_ref`，不是 Key。

Core 在请求授权通过后，通过受限调用链为 `analyze_frame` / `manual_look` 构造临时凭据 payload。Worker 不读 keyring、不收聊天设置或会话，`config_push` 始终无敏感配置。凭据在完成/失败/取消/超时后释放引用；不写日志、磁盘、诊断、请求重放队列或普通备份，也不承诺 Python 内存物理擦零。

当前 Worker 所需请求字段可由屏幕理解适配层填充，不以配置解耦为理由立即改写 `pet-worker/v1`。宿主授权包/实例/profile/操作及目标端点，不能让任意插件借一个引用向任意目标发送秘密。

### 4.3 一次性、可恢复的迁移

1. **解析旧行为**：对每实例分别解析手动 profile，以及自动 `prefer_free_provider`、`vision_same_as_chat` 等开关作用后的有效 profile；包含旧提示词、独立视觉 Key 与聊天 Key 的实际选择规则。不执行网络验证。
2. **脱敏预览和确认**：显示自动/手动将绑定的服务类型、脱敏端点/模型、是否发现凭据，以及“以后不再跟随聊天”的变化。拒绝则不改旧数据，允许在独立包手动配置；不以未确认迁移阻止 Core 启动。
3. **备份和准备**：记录来源指纹、前一目标命名空间及非敏感阶段日志，旧字段留在原配置中作为 legacy 来源，不复制包含未知敏感字段的整份聊天配置。经授权将所需凭据写入新作用域；**不删除、不覆盖聊天凭据，不明文备份 Key**。
4. **验证后提交**：验证新配置 schema、绑定和安全引用可用，原子更新该实例的插件配置；缺失凭据标记待配置，不伪装成功可用。迁移标记记录来源与结果，不含秘密。
5. **中断恢复**：文件与 keyring 不是一个原子事务，阶段日志只记录引用和状态。提交前旧命名空间保持可用；锁内重读并检查修订号后原子合并。恢复只清理本次创建或已替换且不再使用的引用，不覆盖后续用户编辑，不动源聊天凭据。
6. **重复执行**：已迁移且用户修改过的 profile 不被旧聊天配置再次覆盖；恢复/再迁移须明确操作。实例分别处理，不能把多个 slot 的凭据合并。

旧配置解析现在仅用于用户触发的迁移预览/确认；当前内置 Worker、进程内回滚及手动入口缺少 profile 时均不得回读聊天配置。完整恢复合同见[迁移文档](../plugin-phase-01-foundation/PLUGIN-MIGRATION-v4-to-v5.md)。

### 4.4 第二步实施边界与状态

实现见 [screen_understanding](../../pet/screen_understanding/)、[凭据端口](../../pet/credentials.py)和[配置事务](../../pet/config_transaction.py)。配置位于每实例的 `plugins.official.screen-understanding`；普通 JSON 仅含引用，实例由配置文件规范路径隔离。凭据使用系统 keyring，按功能、实例、profile、操作及目标端点授权；后端不可用、写失败或读失败均明确待配置，不保存在会话内存作为替代。

确认迁移核对来源版本，提交在文件锁内重读合并，Core 普通保存保留磁盘上较新的视觉命名空间；安全存储读写不持有配置锁。自动和手动可绑定不同 profile，缺一个不阻塞另一个。配置修订使在途结果失效，关闭自动不禁止手动。

设置使用独立组件；旧聊天视觉页为迁移说明/跳转。第二步当时的联动仅使用受控回调；第四步已接入 §6 的受限文字服务：气泡先展示，聊天缺失、关闭、繁忙或回调失败不影响结果。第二步当时未实现贡献和构建；目前前者已完成、后者已有验证产物，安装卸载仍待实施。完整测试、性能和未验收项见[本步报告](../PR-REPORT-VISION-CONFIG-2026-09-27.md)。

## 5. 接口三：菜单、设置、搜索与快捷键贡献

复用现有 owner、命令和清理机制，补齐 `ContributionRegistry` 合同：注册描述 → 可撤销 handle → 按 owner/版本/实例 scope 撤销。第三步已实现注册身份、批量回滚和清理；第四步由包内 host 提供入口，但不把贡献系统误称为完整安装器。

最小描述包含：`owner`、包版本、稳定贡献 ID、kind、作用域、分组/排序、平台/授权条件，以及命令 ID 或受控设置 factory。命令先绑定，菜单和快捷键引用同一命令，不保存 QAction 对象或任意函数字符串。设置遵守[设置门禁](../SETTINGS-CHANGE-GATES.md)：归属、默认值、保存/迁移/恢复语义、搜索别名及深链唯一。

下表安装状态由 Phase 4B 接续；当前通过显式官方注册或已验证目录加载验证生命周期，不伪造持久安装状态。

| 安装/运行状态 | 行为合同 |
|---|---|
| 未安装 / 已卸载 | 无专属菜单、设置、搜索、命令、快捷键或后台任务；仅 Core 扩展管理可显示安装/恢复信息 |
| 已安装且启用 | 注册入口，Worker 按实际请求需要启动；设置打开/搜索/保存均不截图、不请求模型 |
| 仅关闭自动识屏 | 停自动调度、使该类在途结果失效；手动命令仍可用，不因关闭自动而禁用整个包 |
| 停用整个包 | 先禁止新请求并使全部结果失效，停止 Worker，撤销执行贡献与订阅；保留管理和安全的配置入口，不执行功能 |
| 故障或不兼容 | 撤销不可执行入口，Core 管理页给出原因、重试/回滚；不兼容的 host 不为展示设置而加载 |

保持当前 Menu Action Model / Menu Layout Tree 的分工：排序、隐藏偏好可保留为纯数据，未安装不渲染或绑定；重装先处理 ID/快捷键冲突。包内开关关闭仍遵循现有 Runtime Disabled 语义；**整个包缺失/停用的 owner 撤销不是重写全局菜单树**。托盘和右键共享贡献模型，不在本轮调整菜单布局。

注册中途失败只回滚本批注册，不影响同 owner 的其他批次或其他功能；重复撤销安全。命令与贡献均有唯一注册身份，旧 handle 不能撤销或调用同名新注册。已打开的功能页在停用/卸载时转入安全配置或关闭，默认不丢未保存输入；卸载需说明影响。跨窗口 scope 与生命周期由宿主约束，不重复注册全局快捷键。

### 5.1 第三个切片的实现合同（2026-09-28）

- [ContributionRegistry](../../pet/plugins/contributions.py) 在宿主 GUI 线程提供 owner/scope 绑定端口、能力验证、命令优先批量注册和失败回滚；描述不持有 `PetWindow`/`AppShell`/`Config.data`。旧命令接口兼容，唯一注册身份同时修复旧命令句柄误撤销新注册的边界；`PluginContext.dispose()` 一并释放贡献。
- [FeatureHost](../../pet/plugins/feature_host.py) 由显式官方 factory 提供功能，按窗口绑定命令、按独立执行租约管理共享 Worker。启用、停用、缺失、故障为宿主内存状态，**没有新安装状态文件或用户整包停用开关**。真正安装/卸载的跨进程权威状态由 Phase 4B 接续。
- 屏幕理解拥有 `look_screen`、`proactive_screen` 菜单描述及 factory；Core 适配器只呈现和授权。现代/legacy 均接入，位置、平台限制、文字和排序不变，不新增识屏托盘项。不可用项目不渲染，菜单编辑器仍保存其布局偏好；打开的旧菜单关闭，旧 QAction/回调不能操作新注册。
- [设置组件](../../pet/screen_understanding/contribution_settings.py) 拥有独立视觉编辑与自动策略，宿主在“自动化与联动”挂载设置行、搜索和深链。外层应用只保存策略，不提交视觉/密码草稿；无页面不读取已销毁控件，不用默认策略覆盖旧配置。独立设置进程只挂载组件，不创建完整应用或识屏 Worker。
- 停用整个功能先禁止新执行、使旧代数失效并停止所属执行，保留安全配置页面与草稿。正常移除页面先询问保存/放弃/取消；保存失败不得继续撤销。故障立即禁止执行并拆除组件，在宿主只读文本框保留非敏感草稿，清除密码，不调用故障组件保存；搜索/深链/聊天旧跳转、保存处理器、定时器及信号一起撤销。
- 单窗关闭仅取消该窗口请求和 scope，不能停止其他窗口共享的 Worker；整个 owner 停用才停止共享执行。关闭自动识屏继续允许手动识屏。直接调用兼容入口同样校验权限，迟到结果不展示也不同步聊天。
- 本步不新增全局快捷键，贡献模型仅预留命令引用；第三步当时未实现通用服务及完整受限窗口端口；第四步已接入 §3.2 和 §6。手动执行由包内 host 拥有，旧入口为委托，历史报告不改写。

验收使用真实 Qt 事件循环、窗口和独立设置子进程，只替换外部边界；贡献层未提供功能时禁止加载功能 UI。这**不是整个 Core 可物理删除识屏模块**的证据。逐文件说明、测试、性能及未完成手测见[本步实施报告](../PR-REPORT-SCREEN-CONTRIBUTIONS-2026-09-28.md)。

## 6. 接口四：可选的识屏—聊天联动

### 6.1 最小服务与消息

AI 对话包注册版本化的 `chat.external-turn/v1` 服务（第四步已实现），通过通用 `ServiceRegistry` 得到 owner 绑定的可撤销 handle；屏幕理解以声明且获授权的能力发现服务并定向调用。服务不存在是正常可选状态，不是硬依赖；Core 只验证可用性/权限/路由、捕获错误，**不 import ChatSession/SessionStore 或承担会话业务**。

实际接口为 [ServiceRegistry](../../pet/plugins/services.py) 的 `register(owner, service, route, handler)` 与宿主 `bind()` 得到的 owner 绑定客户端 `call(service, payload)`。路由含 window/instance/character，注册具有独立身份，旧客户端不能误调重新注册后的服务。聊天接收方在有效调用时选择当前目标会话并持久化；不暴露 QWidget、会话对象、列表或数据路径，不实现另一套提前选择会话的 API。

| `ExternalTurn` / 路由字段 | 约束 |
|---|---|
| 来源包、结果 ID、来源 `automatic/manual` | owner 由宿主绑定，不信任调用方自报；result ID 在 Worker 重启和新请求间不复用 |
| 实例、角色、来源窗口、明确目标 scope | 来源有效性由屏幕理解与宿主检查；会话只能由目标聊天服务选择，不接受任意 session 文件路径 |
| `request_text` 与 `analysis_text` | 保留现有请求说明与**完整分析文字**，不是截短气泡；作为一组 user/assistant 外部问答，不解释为系统指令 |
| 路由/失效上下文 | 宿主绑定的目标窗口/实例/角色及服务注册身份、存活状态；过期、已关闭或角色变化时按已定义策略拒绝，不落错会话 |

不传原始截图、API Key、完整配置、任意会话对象；默认不附加窗口路径等额外上下文。现有请求说明可能包含窗口标题，作为用户会话数据处理，不进入通用日志。Core 诊断仅留安全状态与请求标识，不转录问答正文。

这是主进程侧受控服务调用，不借 `CoreEventBus` 向所有插件广播正文，也不把聊天连接到截图 Worker。现有 JSONL 帧上限/错误语义不变；聊天接收的是已经合法返回的完整文字，不能为图省事截短成气泡，也不通过取消大小约束传大对象。

### 6.2 路由与兼容语义

```text
识屏结果返回 → 验证请求/generation/授权/来源窗口 → 原有气泡展示
  → 若允许同步且聊天服务可用
  → 确定目标实例/角色 → 聊天包选择目标会话 → 追加问答
  → 聊天包持久化并刷新可见 UI → 用户后续提问使用该会话上下文
```

- **会话选择时机**：在有效结果交付时解析，而不是提前把请求锁到某个旧会话；保留现状“已有 Chat 窗口用其当前会话，未创建窗口用该角色最近会话、无则新建”的规则。先检查请求是否因角色/窗口切换而失效，再交给聊天包；不静默改变当前选择语义。
- **手动**：只使用发起窗口/实例的路由；窗口关闭、请求取消或 generation 失效后丢弃，不跳到主窗。
- **共享自动**：沿用 shared subsystem 明确管理的有效窗口集合，为每个目标实例/角色分别解析路由并追加。每目标独立成功/失败，不擅自缩成单窗、不向所有插件/陌生实例广播；目标关闭或退出集合后不得继续交付。
- **聊天生成中**：目标聊天服务检查 busy，返回 `busy`，不插入、不打断、不排队；不会因为 UI 未打开而绕过生成状态。已有会话服务可持久化，不要求先创建/显示 QWidget。
- **重复结果**：聊天包按来源 owner + result ID + 目标实例/角色进行幂等消费，成功追加的标记与会话记录一致保存；重试同一结果不得因切换会话再插入一次。新一次“看看屏幕”仍是新结果。只记录已接收项，不为失败/busy/缺服务建立待补发队列。
- **部分失败**：共享目标 A 成功、B 忙碌时各自返回结果；不回滚 A 的合法历史，不重试 B。服务发现后卸载/停用则 handle 失效，返回 `unavailable`，不能触发重新加载或重新安装。

返回状态至少区分 `appended`、`duplicate`、`busy`、`unavailable`、`denied`、`stale_route`、`invalid`、`storage_error`。只有成功持久化才能报告 `appended`；错误隔离后气泡仍然成立。存储失败的安全诊断不得包含 Key、截图或完整正文。处理会话被删除等竞态由聊天包兼容原有语义并测试，不把存储补偿挪回 Core。

### 6.3 所有权与授权

- 屏幕理解负责结果有效性、气泡和是否发起同步；宿主负责定向授权与路由；聊天负责会话、持久化、刷新和后续上下文。
- 两包启用且已有同步授权时自动接通原有联动；缺一包不阻塞另一包。迁移保留原有同步偏好，不暗自扩展权限。该内部服务只向获准的调用者开放，不能靠知道服务名写任意实例。
- 联动只追加文字，本身不请求模型、不传截图、不授予聊天截图权限。后续用户主动提问时才按聊天配置发请求；可讨论的是已保存的分析文字，不承诺无需再次识屏就能追问截图所有像素细节，仍受聊天上下文预算约束。
- 已追加内容成为聊天历史；卸载识屏不删除它。聊天缺失/停用/失败时不在 Core 或识屏包偷偷保存一份待补发历史。
- 迁移期间可由现有聊天代码提供该服务的兼容 adapter，但它的业务代码和数据归 AI 功能包，不能成为 Core 永久硬依赖。聊天也必须有无识屏包启动的验证。

## 7. 接口五：自包含 Worker、独立构建与可信加载

### 7.1 产物与启动描述

首包暂定 `official.screen-understanding`；Worker ID 保留 `proactive-screen`、协议保留 `pet-worker/v1`。一个版本同时交付 host、Worker 与资源：host 使用 Core 已提供的 Qt 和公共端口；Worker **自带执行所需解释器/运行库/依赖**，不要求用户安装 Python，不依赖 Core 里的聊天或截图模块。

第一版接受依赖重复；先测量真实包体/下载体积/启动/RSS，再评估共享运行时，不能为提前省体积重新制造隐式 Core 依赖。Pillow、keyring、certifi 等有其他使用者，不能不经审计就从整个项目删除或全划给识屏。

经验证的 `VerifiedFeatureDescriptor` 最少提供 owner、版本、API/Core/平台约束、受控 host factory 标识及包内文件映射、Worker 相对程序路径与固定参数、能力声明、验证证据和版本租约。实际绝对路径从已验证版本根解析，不接受任意命令。它表示验证结果而非“已安装”；当前验证入口显式注入描述，不自动扫描或写入安装状态。

- host 只从已认证官方包加载，按受控 factory 契约注入窄 `FeatureHostContext`；不执行内容 manifest 的 `entrypoint`，不修改全局搜索路径来导入未知插件。
- Supervisor 接收**程序路径 + 参数数组**，不用 shell。Worker 仍用现有 ID/协议握手；独立产物不能因启动失败切回同一 Core 可执行文件来执行识屏。
- Worker 从包内资源/运行库启动，运行数据写独立数据/缓存位置，不写 Core 或不可变版本目录。清理继承的构建/模块搜索污染，禁止通过 Core `_internal` 补齐缺失依赖。
- GUI 内的官方 Python host 不是强安全沙箱；受限端口是工程/授权边界，不能防御任意恶意 Python。信任官方发布者、加载前验证和禁止第三方任意代码仍必要。

### 7.2 执行前验证

当前实现只接受显式版本目录：校验受限路径、重复/大小写冲突、符号链接/重解析点/硬链接、完整文件清单、大小/SHA-256 及 API/Core/平台/能力，再验证**发布者签名**，通过前不执行包代码。ZIP 解压和 Setup 来源归 Phase 4B/5A，必须接入同一验证描述，不能绕过校验。

`manifest.sig` 是 manifest 的分离签名；manifest 的受签字节覆盖版本、加载描述及全部 payload 文件摘要，清单不自引用 `manifest.sig`。宿主信任锚来自 Core 受控发布，不接受包自带公钥为自己背书；拒绝重复字段/模糊解析及未登记的执行文件。加载时仍核对已验证版本，避免校验后被替换。

第四步使用 `cryptography` 的 **Ed25519** 验证 manifest 原始字节。隔离验证构建使用一次性测试私钥，完成签名后不保存私钥；测试公钥只写入明确标记的验证产物，不进入正式信任锚。正式发布密钥、轮换和平台签名仍待发布门；资源包签名占位接口不因此自动升级为代码加载器。加载器捕获已验证 host 源码并以版本隔离命名空间加载，不修改全局 sys.path；Worker 启动前再次校验。

开发态未签名加载必须显式启用、可诊断并与正式安装状态区分；不放松路径、兼容和权限检查，也不能把开发产物标成正式可信。签名证明来源/完整性，不证明代码没有 bug。

### 7.3 构建隔离的证据

第四步已生成并验证两种无识屏 Core（含聊天/无聊天）和一份自包含屏幕理解包；证据见[实施报告](../PR-REPORT-SCREEN-HOST-BUILD-2026-09-29.md)。持续验收必须保留对应源码/构建输入：无识屏包的 Core，及自包含屏幕理解包。核对 PyInstaller TOC/import 图和实际文件，不能只把未使用模块藏进 PYZ 后声称移除了。

- Core 基础路径不导入识屏、Pillow 截图或视觉请求实现；其他功能合法共用依赖单列依据，不能误删。
- 识屏产物不能 import 聊天业务、会话/Chat UI 或从 Core 取 Provider 类；必要 HTTP/模型适配随包构建，按当前代理行为回归。
- 在没有聊天包、没有源码目录/PYTHONPATH 救场的隔离安装环境验证识屏；同时验证聊天存在时的可选同步。
- Windows 子进程必须验证 DLL 搜索边界、外部 PATH 污染、Core/PySide6 与 Worker 自带依赖的互不补齐/抢载。使用真实独立冻结产物及 Qt/Worker smoke，记录实际解析来源；其他平台另验，不能据此宣称已跨平台。
- 现有完整 onedir 或“同一 EXE 的 --worker”通过仅证明 Phase 3B，不作为最小 Core/自包含交付证据。

## 8. 安装状态、目录与卸载边界

当前只加载显式已验证目录，host/设置/Worker 复用同版描述及进程内使用句柄；host 已加载即保留版本占用至进程结束，不承诺 Python 热卸载。跨进程占用、state.json 和安装事务尚未实现。

沿用当前应用数据根解析，版本文件与配置/用户数据分离。以下是 **Phase 4B 待实施的相对布局合同**，不是现在可复制文件安装的路径：

```text
<现有应用数据根>/
  plugins/official.screen-understanding/
    state.json
    versions/<version>/
      manifest.json
      manifest.sig
      host/
      worker/
      resources/
    data/<instance-id>/
    cache/
```

`state.json` 是功能包安装状态唯一权威，记录 schema、已验证版本、active/previous、事务阶段及待重启动作；不把目录存在或配置残留当成已安装。启用偏好仍按实例配置管理，执行必须同时通过安装状态、实例启用和授权。Phase 1 角色包的 `active.json/previous.json` 不因该新合同被改写。

普通配置沿用各实例 `plugins.<plugin_id>.schema_version/settings/legacy`，不在版本目录再存一份权威配置；Key 留在安全存储。data 按实例隔离，cache 不保存截图/Key，也不保存等待聊天接收的正文。版本与用户数据分离使默认卸载可保留偏好；清除数据/凭据另行说明并确认。

host 与 Worker 必须原子切换到**同一包版本**。宿主持有覆盖 host 模块、设置页和 Worker 的版本租约；多个实例/进程协调停止并释放，不能仅凭 PID 或删除目录判断不再占用。切换/删除失败保留旧版本与恢复日志，崩溃后的租约恢复需真实进程测试。

停用/卸载顺序：禁止新请求与失效所有 generation → 停任务/Worker → 撤销贡献与服务路由 → 协调实例/租约 → 切换状态或移除版本。不能即时释放的 Python 模块或文件锁，显示**待重启完成卸载**，之后不得继续执行，不承诺 Python 热卸载。卸载屏幕理解不得清除聊天历史或重装其他包。

独立交付后 Worker 故障先有限重启；耗尽后暂停功能，保留诊断/显式重试/版本回滚入口，**不在 Core 执行截图或网络 fallback**。用户停用/卸载不能触发重启。当前 3B `auto/in_process` 运行模式仍保留，但两条路径已改用独立视觉配置；资源角色 fallback 是另一合同。

Setup、ZIP 与应用内管理在 Phase 4B/5A 使用同一事务；Core 更新不能重新装回已卸载功能。归档扩展名/打包容器、最终发布 ID、便携标记及各平台绝对路径需在相应实现门核对；不因这棵相对树调整现有数据根或密钥存储。

## 11. 你最终会得到什么

- **只装识屏**：可独立设置视觉服务、自动识屏或手动“看看屏幕”；无需安装聊天。
- **只装聊天**：可正常对话/文件理解，不获得截图权限，不启动识屏进程。
- **两者都装并启用**：像现在一样，看完屏幕后能在聊天里看到全文并接着问；聊天窗未打开也能保存。聊天正在回答时跳过本次同步，不打断、不偷偷补发。
- **卸掉其中一个**：另一个继续工作；识屏卸载不删除已有聊天记录。卸载默认保留各自偏好，重装可恢复。
- **进程怎样连接**：屏幕理解 host 运行在主进程，但代码随功能包交付；它通过本机 `QProcess + stdin/stdout JSONL` 管理自包含 Worker。聊天只接收受控文字，不直连截图 Worker。
- **文件放哪、怎么装卸**：目标结构见第 8 节；Phase 4B 提供本地导入/应用内卸载，Phase 5A 接安装向导选装和 ZIP/便携。当前只有验证工具显式加载已签名版本目录；不要把验证目录当成正式安装状态，也没有应用内安装/卸载按钮。

当前四个切片均已有自动化基线，第四步形成 Windows 独立验证产物。设置 → 自动化与联动 → 屏幕理解可预览并确认迁移，或手动配置自动/手动 profile；安全存储失败保持待配置。关闭聊天不会改变已配置识屏，两者启用仍可同步分析文字。代码/产物边界已在验证变体中分离，现有默认构建不替换，正式安装路径与卸载体验仍不变。此前手动识屏正常的用户反馈不是本轮配置变更的验收；新设置/安全存储、自动识屏和托盘退出仍待人工确认，**不因此推断自动识屏有 bug**。

## 10. 基线评审后的安全与身份边界（2026-10-02）

Phase 4A 的运行边界不应被宣传成安全沙箱：

- Core 与 Worker 默认使用同一 OS 用户权限；`QProcess` 隔离崩溃和阻塞风险，但不阻止 Worker 自己访问其可访问的系统资源。
- `PluginContext`、capability 和贡献 owner 限制可调用的宿主 API，不保证阻止死循环、阻塞 I/O、内存耗尽或 native crash。
- 事件总线能隔离可捕获异常，不能代替进程级故障和资源限制。
- 功能 host 不接触完整 `PetWindow`、`PetApp` 或全局 `Config.data`；设置/菜单只拿受限端口。

后续接口和测试明确区分：`data_root_id`（数据根）、`config_slot_id`（配置槽）、`window_id`（窗口）、`process_id`（进程）、`host_id`（功能 host）、`service_id`（服务）和 `worker_id`（Worker）。权限、配置、结果路由和租约不能用“实例=进程”一句话替代。
