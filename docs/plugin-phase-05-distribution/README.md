## 1. Phase 5A：小 Core Setup 内嵌选装与 ZIP/便携

依赖 Phase 4 的真实屏幕理解样板和统一事务，交付：

- 小 Core Setup 提供官方组件选择，官方 ZIP 直接嵌入安装器；没选不安装，选中后自动导入/启用，失败只影响对应包，不读取 Setup 旁置 `packages`，也不偷偷联网补装。
- ZIP/目录可通过应用显式导入本地功能包；先受限读取 manifest 自动路由，未知 owner 只要符合注册、兼容、完整性和固定 host/worker 合同即可作为第三方 DLC。复制文件不会自动执行，用户选择导入才建立信任边界。
- 显式便携模式使普通数据和 DLC 随便携根迁移；默认模式仍使用平台数据目录。便携标记、目录布局、只读路径处理和实例锁范围是实施前设计产出，不在此凭空冻结。
- 功能包导入不携带发布私钥，也不要求用户提供公钥；Provider 偏好、会话等普通数据与秘密区分，凭据仍由操作系统安全存储管理。
- Setup、ZIP、应用内扩展管理共用 [Phase 4 安装事务](../plugin-phase-04-updates/PLUGIN-UPDATE-PROTOCOL.md)、版本/依赖解析和权威安装状态。Core 更新尊重卸载记录，不重新装回选装功能。
- 主桌宠始终提供扩展管理；本地导入、启停、配置、卸载、故障/回滚不等待远程 catalog。第三方包按 owner 隔离配置和数据，已加载 Python host 的替换以重启生效。

**出口**：干净安装最小 Core；离线选装/未选/缺包三种 Setup 路径；ZIP 导入；显式便携迁移；卸载/重装；多个实例占用；升级与 Core 更新不复装。记录 Core、内嵌 DLC 包、下载/解压后体积及启动成本；真实系统安装矩阵需单独授权。

## 2. Phase 5B：AI 对话优先，推广全部官方领域

[功能交付总表](../plugin-roadmap/PLUGIN-FEATURE-DELIVERY-MATRIX.md) 是唯一主要归属清单。11 个逻辑领域不等于 11 个 ZIP 或 Worker，现有 ID 和数据不能因为分类变化直接改名迁移。

顺序：

1. 屏幕理解样板先完成；期间可以准备 AI 的 UI、数据、依赖、密钥和构建审计，不同时大规模重写。
2. **样板稳定后，AI 对话与文件理解是下一项主要拆包实施目标**，不是未来有需求才补的功能。
3. 随后推进 Agent/外部工具，并按依赖审计确定账户用量、音乐、语音报时、生活提醒、日常台词、灵动岛、趣味互动、快捷启动的具体批次。
4. 每个领域都进入交付跟踪；允许共享受管理的依赖或合理合包，但不得以合包使本应独立使用的能力变成强制安装全家桶。

其余批次和包数量待审计确认，官方可选交付本身不再条件化。Phase 3C 是否新增 Worker 与这里是否拆包分别决策。

## 3. AI 对话与文件理解的边界

- Chat UI、快捷对话、Provider 配置、流式请求、会话/附件与现有文本文件解释归 AI 功能包。
- Chat QWidget 可暂留 GUI 主进程，但代码、专属设置和会话策略随 AI 包交付；网络/Provider 执行单独评估 Worker，现有 QThread 不是独立进程。
- 会话、角色/实例隔离、未完成写入、附件路径、密钥引用、备份和回滚必须纳入迁移；卸载默认留数据，重装验证可恢复。
- AI 不依赖灵动岛或屏幕理解，安装聊天不授予截图权限；屏幕理解可独立配置视觉服务，同步聊天是可选联动。
- 共用模型/视觉请求采用窄接口或显式公共依赖，不能把全部 AI 实现重新放回 Core。
- 现有文本/代码文件解释与模拟投喂分开，后者不得修改真实文件。不扩展为未实现的通用 PDF/二进制解析。

## 4. 菜单、设置与独立使用

所有领域采用同一 [贡献生命周期合同](../plugin-phase-01-foundation/PLUGIN-API-CONTRACT.md)：未安装无专属菜单/设置/搜索/快捷键；启用后注册；停用不执行但可管理；故障可诊断；卸载按 owner 撤销，保留排序和偏好。

生活提醒没语音包也能显示文字；Agent 基础状态不依赖余额；日常台词可离线；角色与基础桌宠不依赖任何功能包。贡献机制服务于这些独立使用要求，不提前全面重排菜单。

## 5. 条件来源适配器

GitHub Release、CDN/镜像、组织源和 Steam Workshop 只在实际分发需要时接入，负责发现/下载后交给统一事务；Workshop 独立 adapter，不进入 Core 基础加载逻辑，不提前引入 Steam 依赖。第三方生态留给 Phase 6，不阻碍官方包发布。

## 6. 验收与失败恢复

每个已承诺包必须提供：无包 Core 可用 → 安装后入口/能力可用 → 停用不执行 → 卸载文件与入口消失 → 重装恢复偏好；另测权限/离线/依赖/多实例/升级回滚/包体。只增加 Worker 数或隐藏菜单不算通过。

Setup/来源适配失败保留应用内本地导入和 Core；单个包失败禁用或回滚该包，不回装已卸载功能，不破坏其他包和数据。未完成领域如实列为未交付，不宣布全部选装完成。

## 7. 给使用者的效果说明

安装向导可以只装桌宠本体，或选装旁边的官方包；ZIP 版以后也能在桌宠里导入和卸载。普通安装的包和数据在受管理数据目录，便携模式放在显式便携根下，具体名称在实现前确认。功能自己的 UI 可在主进程，Worker 通过本机管道连接；不装就没有对应入口和后台任务。

先做到屏幕理解可拔除，然后重点拆 AI 对话与文件理解，之后推广其余官方功能。当前这些安装步骤仍是目标，不是已有用户操作说明；第三方市场暂时没有也不会卡住它们。

## 6. 外部基线评审后的进入门（2026-10-02）

Phase 5 的远程分发不能绕过本地可靠性。进入远程 catalog/下载前必须证明：

1. Phase 1 P0 资源解析、冲突清理、Starter/Core 更新保护和实际播放 E2E 通过；
2. 本地状态、真实租约、安装/升级/卸载/恢复和延迟 GC 通过；
3. 包签名、正式信任根、`key_id`、轮换、撤销和离线策略明确；
4. catalog 签名、新鲜度、回滚保护、下载重试和解压/磁盘限额明确；
5. Windows 真实构建、文件占用、跨卷和杀软/EDR 失败有分类证据；
6. 报告命令、环境、样本量和测试数可复现。

本地目录、本地 ZIP、远程 catalog 和 Workshop 继续分开；Workshop 只是条件 adapter。远程能力未完成时，应用内本地导入和 Core 启动仍可用。

## 7. 资源硬门与远程分发前置（2026-10-02）

Phase 5 的远程 catalog、下载、签名和新鲜度策略不能绕过 Phase 4B-1.5。进入远程分发前必须证明：目录/ZIP 安装都能被 Registry 正确解析并实际播放；冲突包不破坏旧 active；Starter/Core 更新不删除用户资源；派生 cache 不进入内容身份；卸载中断可恢复；4B-1 状态、4B-2 租约和 4B-3 本地事务具有可核验记录。正式信任根、`key_id`、轮换、撤销、离线策略和 catalog 新鲜度仍需单独冻结。

在这些门通过前，本地资源样例和作者工具只能作为内部验证材料；Workshop、远程下载和复杂分发不成为本地资源可用的前置，也不应被宣传为已经完成。

### 完成后的实际使用效果

这一阶段不会自动增加远程下载按钮。它保证未来即使接入 catalog，下载到的资源也先经过“安装后真的能播放”的本地硬门，而不是只显示安装状态成功。
