- **日期**：2026-10-02
- **主题**：参考 VPet 设计 DLC 开放顺序，并确定用户自制功能的第一批接口边界
- **状态**：已完成本轮对齐
- **本轮性质**：架构与产品路线讨论；未修改运行时代码、测试、构建配置或安装管理实现

## 1. 用户问题

用户希望参考 VPet 的 MOD 思路，确认以下问题：

1. 资源 DLC、官方功能 DLC 和用户自制功能能否同时准备；
2. 暂时不接入 Steam/Workshop 的情况下，用户能否根据我们提供的接口制作自己的功能；
3. DLC 应该按什么顺序开放；
4. 别人的 DLC 数据如何存储；
5. 什么时候可以声称 Python host 支持即时热卸载。

## 2. 事实与参考

VPet 的官方项目把资源 MOD 和代码插件纳入同一扩展生态，并提供插件示例。其代码插件加载方式可以直接从 MOD 目录加载程序集并构造插件，插件获得 `MainWindow` 入口；这提供了直接、易上手的扩展体验，但也意味着主窗口和插件之间存在较深的实现耦合。

本轮参考资料：

- [VPet 官方 README](https://github.com/LorisYounger/VPet/blob/main/README.md)
- [VPet `CoreMOD.cs`](https://github.com/LorisYounger/VPet/blob/main/VPet-Simulator.Windows/Function/CoreMOD.cs)
- [VPet 插件示例](https://github.com/LorisYounger/VPet.Plugin.Demo)
- [VPet MOD/插件校验逻辑](https://github.com/LorisYounger/VPet/blob/main/VPet-Simulator.Windows/WinDesign/winGameSetting.xaml.cs)

本项目借鉴 VPet 的统一扩展体验，不直接复制任意代码进入 Core 的模型。

## 3. 本轮推荐答案

### 问题一：是否可以同时做

**可以并行准备，但不平级开放。**

可以并行推进：

- 资源 DLC manifest、示例和作者模板；
- 官方屏幕理解功能包；
- AI 对话功能包的依赖审计；
- `pet-worker/v1` 文档和跨语言 Worker 示例；
- 菜单、设置、命令、数据和凭据贡献接口。

不能同时对外承诺完成：

- 任意 Python host 进入 Core；
- Python 模块无重启热卸载；
- 第三方 Worker 正式 SDK；
- 自动远程下载和复杂社区分发；
- Steam/Workshop；
- 没有安装事务、租约和恢复机制的“可卸载功能 DLC”。

推荐按照风险和依赖逐级开放，而不是等待所有官方功能完成后才开放资源创作。

### 问题二：第一批用户自制功能采用什么边界

推荐：

```text
资源 DLC + 外部 Worker
暂不开放任意 Python host 进入 Core
```

用户可以先制作不执行代码的资源包；后续可以使用任意语言制作独立 Worker，通过受限 JSONL 协议接入桌宠。

## 5. 最终决策

### 5.1 开放级别

```text
资源 DLC：最早开放
官方功能 DLC：由项目先完成真实安装/停用/卸载样板
用户自制 Worker：官方样板稳定后进入开发预览，再正式开放
任意 Python host：条件评估，不作为当前路线承诺
Steam/Workshop：暂不实施
```

### 5.2 对外接口层级

计划提供以下相互分离的接口：

- `pet-content/v1`：纯资源包描述、校验、兼容和内容注册；
- `pet-worker/v1`：外部 Worker 的 stdin/stdout JSONL 生命周期、请求和事件协议；
- `feature-contribution/v1`：菜单、设置、搜索、命令和快捷键贡献及 owner 撤销；
- `feature-data/v1`：实例/共享命名空间数据读写；
- `feature-credentials/v1`：由 Core 代理的安全存储和单次请求凭据。

这些名称先作为路线和设计标签；正式稳定版本、字段兼容矩阵和第三方 SDK 发布门仍需在后续阶段冻结。

### 5.3 数据存储原则

- 包代码和资源进入不可变 `versions/<version>/`；
- 用户配置、会话、记忆、统计和偏好进入插件自己的 `data/`；
- 可重建内容进入 `cache/`；
- 密钥通过 Core 和操作系统安全存储处理，不写入 JSON、manifest、备份或 Worker 配置快照；
- 数据包含实例 ID，不能跨 `config-slot-N` 覆盖；
- 普通卸载删除包代码和入口，默认保留用户数据；
- 清除数据必须是单独且明确的用户操作。

### 5.4 “Python host 可以即时热卸载”的判定

当前 Core 内 import 的 Python host 不能宣传为热卸载。停用、销毁、撤销贡献和停止任务，只能称为逻辑停用或待释放。

外部 Worker 通过进程退出和租约释放后，可以称为进程级卸载；这不等于 Python 模块热卸载。

只有未来把 host 放进独立 Feature Host Process，并证明 Core 无 host 引用、进程和 Worker 都退出、贡献全部撤销、文件可删除、重装可恢复，才能宣传“无需重启 Core 的进程级功能卸载”。这属于 Phase 6C/Phase 7 的条件目标。

## 6. 设计树结论

```text
DLC 生态
├── 资源 DLC
│   ├── 纯数据
│   ├── 先开放
│   └── 本地目录/ZIP，不依赖 Steam
├── 官方功能 DLC
│   ├── 屏幕理解优先
│   ├── AI 对话与文件理解随后
│   └── 先由项目验证完整管理闭环
├── 用户自制功能
│   ├── 第一批：外部 Worker
│   ├── 任意语言实现
│   ├── 受限贡献、数据和凭据接口
│   └── 暂不允许任意 Python host 进入 Core
└── 条件生态
    ├── Feature Host Process
    ├── 更深的 UI 扩展
    ├── 远程分发
    └── Steam/Workshop（当前不做）
```

## 7. 待后续单独决定的问题

这些问题没有在本轮提前冻结：

1. `pet-content/v1` 的最终 manifest 字段和资源类型；
2. 第三方 Worker 的签名、审核和权限细节；
3. Worker 是否允许开发态脚本直接运行，以及如何与正式可执行文件区分；
4. Feature Host Process 是否值得实现；
5. 第三方 Worker 是否需要远程 catalog；
6. 真实用户生态开放时的兼容矩阵和弃用策略。

这些问题进入对应 Phase 5/6/7 计划，不反向扩大当前 4B-2。
