桌宠的「内核 + 插件」是怎么搭起来的

petcore 把旧版单个 pet/ 包拆成了 core 与 mod：core 只负责让桌宠活着、能交互、能管理扩展； 角色是 content 包，功能是 feature 包。下面这张长图按「分层 → 启动 → 插件流水线 → 端口 → 线程 → 小游戏可行性」组织， 每个结论都能在文末找到对应的源码位置。

01

一页结论

先把「谁负责什么」记住，后面的图都只是这句话的展开。

core 的职责，只有三件事

  1. 让桌宠活着：窗口、渲染、动画链、行为决策、物理与碰撞、气泡、托盘、灵动岛。
  2. 让用户能配置：设置窗口、菜单布局、热键、自启、多宠 profile、数据目录与迁移。
  3. 让扩展能挂上来：发现/校验/安装/启停 mod，提供 HostPorts，托管设置页与对话窗槽位。

core 不认识「天气」「抽签」「AI 人格」这些业务词；这些都在 mod 里。

三类产物，别混着放

feature
能带 Python 代码（entrypoint），提供菜单、命令、设置页、对话窗页。装到 <data_root>/mods/<id>。
content
角色/素材包，不能带可执行文件。id 形如 character.<名字>。
内容块
sounds / themes / phrases / seasonal：loader 会读成 ContentEntry，但当前运行期没有消费方（详见 §05）。
一句话版本 core = 运行时 + 窗口壳 + 扩展宿主；mod = 业务逻辑 + 业务 UI + 业务数据。 mod 与 core 之间只有两条正式通道：contributions（菜单/设置页/对话窗页）和 HostPorts（22 个已注入端口）。 其余路径（直接 import core 实现、自己开窗口）要么被架构测试拦，要么属于「文档允许但后果自负」。

扩展平面：不在上面的栈里，但每一层都能看到它

03

启动路径：一只桌宠是怎么出现的

正常启动与 --check 走同一条内容链路；区别只在于后者不创建窗口、不写配置。

1
解析参数petcore/cli.py

--root 定数据根，--portable / --instance 换根，--allow-feature-mods 打开功能扩展总开关，mods 子命令走 CLI 分支。

2
加载全局配置Config.load(data_root)

读 config.json、各 slot 的 config-pet-N.json、overlay-active-pets.json；--check 用 persist=False，不落盘、不建迁移备份。

3
单实例锁QLockFile

同一数据根只允许一个进程；--instance NAME 用独立数据根与独立锁，可以并行开多份。

4
创建 CoreHostpetcore/ui/app.py:398

进程级服务在这里组装：QtScheduler、音频路由、记忆、Webhook、API 规格与钥匙串、账户/余额、语音与 ASR、DSH 客户端、社区、聊天/快速对话控制器、截图问答、菜单模型、免打扰、WorkerHost、市场任务。

5
加载内容与扩展CoreHost.load_content · mods/loader.py

只读加载 assets/characters，再扫描 mod 目录；content 包进角色列表，feature 包过 manifest 与授信闸门后由 FeatureManager 装配。

6
创建宠物窗口PetManager / PetWindow

动画目录 + 播放器 + 行为导演 + ClipLibrary（frameseq → webm → gif 回退）；恢复位置/屏幕/缩放；渲染首帧后显示。多宠时 slot 1..98 各自有 profile。

7
装配端口并启动 runtimeui/ports.py::build_ports:981

27 个端口字段里实际注入 22 个；内置 7 个 Core 特性无条件加载，用户 feature 通过 runtime.start() 起来，菜单贡献合并进「扩展」子菜单。

8
托盘、菜单、监听器TrayIcon · MenuModel · SessionWatcher

托盘菜单独立于右键菜单；屏幕变化、锁屏/睡眠、全屏检测、灵动岛采样按需启停——空闲时不该有常驻定时器。

9
进入事件循环QApplication.exec()

之后所有 GUI 操作都在主线程；mod 的跨线程回调统一经 QtScheduler 排队。

--check 是排障第一入口 它输出角色、每段动画实际采用的后端、mod 列表与诊断、配置快照（menu_template=json|builtin、speech、self_talk_images 等）。 构建门用的是 --check --strict；普通 --check 只读，不该写任何文件。
04

插件流水线：从磁盘上的一个目录到菜单里的一项

这是 feature mod 的完整生命周期。每一步失败都只产生一条诊断，不会阻断 core 启动。

1. 扫描数据目录 mods → 安装目录 mods → 仓库 mods → 额外目录；同 id 后者覆盖，记诊断
→
2. 校验mod.json schema、id、version、api_version、路径逃逸、content 包禁可执行文件
→
3. 授信闸门feature 必须在 user mods 内，且 allow_feature_mods 或安装目录 .trusted
→
4. 导入入口entrypoint 必须包内相对路径；host/__init__.py 按包加载，支持相对 import
5. create_host收到 FeatureContext（owner / core_version / api_version / ports / host / log）
→
6. FeatureDefinitioncontributions + runtime_factory + settings_factory + view_factories
→
7. runtime.start()订阅、定时器、加载数据；命令表 runtime.commands 在此暴露
→
8. 贡献落地菜单项 / 设置页 / 对话窗页进入 core 的 UI 槽位

命令是怎么被点到的

  1. 菜单贡献 id 统一成 <owner>:<contribution>，默认进「扩展 → <manifest 名字>」二级子菜单。
  2. 点击时 core 取该菜单项的 data.command（缺省等于贡献 id），再调 FeatureManager.command(owner, command_id)，拿到 runtime 的 commands 字典里那一项。
  3. 命令函数如果声明了 slot 形参，core 会把发起菜单的那只宠的 slot 传进来。
  4. 命令抛异常：记日志并气泡「扩展执行失败，详情见日志」；core 不会崩。

停用 / 卸载的顺序

  1. stop_owner()：先撤销 speech / reminders / interaction 的 owner 订阅，再 runtime.stop()。
  2. 菜单模型注销该 owner 的所有节点。
  3. 清掉包目录下的 sys.modules，避免旧模块继续存活。
  4. 有 install.json 的按清单删文件；无清单的（安装器投放）整目录删。
  5. 个人数据永不删：feature-data/<id>、配置键、钥匙串都保留。
三个容易误会的点
  • execution: "worker" 合法但永远不会被加载，只在日志里留一句 worker feature is not supported yet；今天只支持 host-only。
  • capabilities 是声明，不是沙箱：写不写、写什么，运行期都没有强制检查。
  • 没有 Python 模块热卸载；「重新加载扩展」是停掉 runtime、清模块、重新导入，不是你代码里的模块级状态能全身而退。

07

线程模型：只有 scheduler 是「任意线程」

这是写 mod 最容易踩、也最难在测试里发现的一类问题：在后台线程碰了 Qt 控件，平时没事，用户点一下审批卡就整个应用挂起。

GUI 线程 主线程

  • 所有 Qt 控件、窗口、气泡、菜单、托盘。
  • presentation、pets、interaction、audio、screen、reminders 的调用。
  • 命令回调、scheduler 的定时回调、interaction.on_tick。
  • 你的游戏窗口里的 QTimer 与 paintEvent。

后台线程 你开的，或者 core 的回调

  • http.request / get_json：同步阻塞，自己开线程。
  • speech.synthesize：阻塞；speak 才是异步入口。
  • config.set、storage.data_dir：会碰磁盘。
  • screen_ask.on_ask / on_action：回调本来就在后台线程。
  • chat.append/open 与 presentation 现在可从后台调用，但实现只是帮你排队——别指望同步效果。

六条铁律

  1. 回 GUI 只用 ports.scheduler.call_later(0, cb)。它是唯一明确允许从任意线程调用的端口；回调一定在 GUI 线程执行。
  2. 不要在 worker 里建窗口、碰气泡、改控件。哪怕只是 QLabel.setText()，也可能在 Windows 上变成 AppHang。
  3. stop() 里先取消，再清状态：scheduler.cancel(handle) / cancel_owner(owner)；订阅的注销函数也在这里调。
  4. Runtime.close() 永远不会被 core 调用。清理写在 stop() 里，或者让 close = stop。
  5. 重活下后台，结果回 GUI：解码、读大文件、网络、语音合成都不要在 on_tick 或 QTimer 回调里做。
  6. 迟到的结果要丢弃：用代次号 / 取消事件 / guard，别让上一局的结果写进下一局。
为什么桌宠对线程这么敏感 它每 16ms 有一条动画/碰撞节拍，同时还有透明窗、置顶、气泡从属窗口这些 Win32 层级关系。 一旦某个 mod 在后台线程直接 show() 或改控件，Qt 的事件循环会被跨线程的窗口消息拖住，表现就是「点一下卡死几秒」。 正式契约因此把 GUI 亲和写死；实现层的排队只是兜底，不是让你随便调。
08

协作者想做一个小游戏 mod：能做到吗？

这是本文最重要的一节。结论、三条 UI 路线、游戏循环、数据、素材、分发和已知坑，都按「今天的工作区」给。

可以做
边界要清楚

能。新 UI、新功能、新数据都能加，而且不需要改 core。

这是一个 feature mod：一个目录、一个 mod.json、一个 create_host()，再加你自己的窗口、逻辑和存档。 官方的 fun.divination 已经在命令里惰性开 QDialog，tool.ai-browser 已经在对话窗里放整页 QWidget—— 两条路都有人走过。

但它不是「独立程序」：和桌宠同一个进程、同一个 Python 解释器、没有沙箱、没有窗口生命周期治理、只支持 host-only。 下面四条边界要自己扛。

先选 UI 路线：三条，推荐第一条

① 自建窗口 推荐

棋盘、卡牌、实时玩法、带画布的游戏
  • 用 QDialog / QMainWindow，在菜单命令里惰性导入。
  • 窗口 chrome、圆角、置顶、跟随、关闭清理都由你负责。
  • 先例：fun.divination/host/runtime.py::show_card。

② 对话窗里的一页 chat_view

助手式面板、网页、状态页、轻量互动
  • Contribution(kind="chat_view") + view_factories。
  • core 管标题栏按钮、槽位、圆角、深色、生命周期。
  • 不是独立窗口；每次开对话窗都回到 AI 页，别指望做默认页。

③ 设置页

规则、难度、音量、存档管理
  • 继承 SettingsPage，进「扩展管理」的页内导航。
  • 内容在 QScrollArea 里，默认阅读宽 860；别把棋盘塞进来。
  • 保存/取消/回滚语义由 core 统一委托。

游戏循环：按节奏选，不要一律上 16ms

回合制 / 棋盘 / 卡牌

不需要帧循环。按钮、QTimer.singleShot、动画结束信号就够了。

窗口关闭即停；没有常驻定时器，桌宠的待机帧率不受影响。

实时 / 动作 / 弹幕

两种写法：自己窗口里的 QTimer(33ms)，或 ports.interaction.on_tick(owner, cb, 16)。

两者都在 GUI 线程；只做轻量状态推进与 update()，重活下后台。窗口隐藏/关闭必须停表。

别用 on_tick 驱动一个看不见的游戏 16ms 回调即使在窗口关闭后也会继续跑，既烧 CPU 又会让「一局」在后台偷偷推进。正确做法：窗口 showEvent 启动、 hideEvent/closeEvent 停止，runtime.stop() 再兜底取消。

数据：存档进 feature-data，偏好才进 config

能力 → 端口对照表

小游戏需要用什么注意
一个新窗口 / 一块画布自己的 QDialog / QWidget没有窗口端口；引用自己持住，关闭停表
每帧推进QTimer 或 interaction.on_tickGUI 线程；窗口不可见就停
存档 / 排行榜 / 回放storage.data_dir原子写；版本号；卸载不删
难度 / 音量 / 开关config + settings_page只放偏好；extra 限额
音效 / BGMaudio.play(path)文件在包内；大文件别在 GUI 线程解码
桌宠说话 / 表情 / 动作presentation、pets动画名必须存在于当前角色；缺了就安静降级
开局入口menu contribution + runtime.commands命令声明 slot 才知道是哪只宠
拖文件当输入interaction.on_drop拿到的是已投喂的文件路径列表
联网对战 / 拉排行榜http阻塞；自己开线程；结果经 scheduler 回 GUI
语音播报结果speech.speak可能失败；不要用 on_done 冒充播放完成
在对话窗里开一页chat_view只给槽位，不给窗口
全局快捷键开局没有全局热键是 core 的；窗口内可用 QShortcut

四条必须接受的边界

边界 1 没有窗口端口

core 不提供「给我一个受管窗口」的接口。置顶、跟随桌宠、多宠归属、关闭清理、几何持久化，全部你自己写。 文档明确说：别自己再造聊天窗；要占对话窗的一页就用 chat_view。

边界 2 与桌宠同进程

你的死循环会卡住桌宠的 16ms 节拍；原生崩溃会带走整个应用。重活必须下后台线程， 长时间任务要有取消与超时。

边界 3 能力不是沙箱

capabilities 只是声明，运行期没有闸门。mod 理论上能读文件、起进程、联网。 信任来自「安装位置 + 用户勾选 allow_feature_mods / 安装器 .trusted」，不是代码里的权限检查。

边界 4 只支持 host-only

execution: "worker" 合法但永远不会被加载。没有独立进程隔离， 也没有 Python 模块热卸载；「重新加载扩展」需要你的 stop() 把窗口、定时器、线程都收干净。

host/runtime.py：无 Qt 的运行时

import logging
from pathlib import Path

OWNER = "game.board"
ASSETS = Path(__file__).resolve().parent.parent / "assets"
log = logging.getLogger(OWNER)


class GameRuntime:
    def __init__(self, context):
        self.ports = context.ports
        self.commands = {"play": self.play}
        self._window = None

    def play(self, slot=None):
        if self._window is not None:
            self._window.raise_()
            self._window.activateWindow()
            return
        # Qt 只在 GUI 线程的命令里惰性导入
        from .game_window import GameWindow

        self._window = GameWindow(on_finish=lambda score: self._finish(slot, score))
        self._window.finished.connect(self._forget_window)
        self._window.start()

    def _forget_window(self, _code=0):
        self._window = None

    def _finish(self, slot, score):
        target = None
        if self.ports.presentation is not None:
            target = self.ports.presentation.for_slot(slot) if slot is not None else self.ports.presentation
        if target is not None:
            target.say(f"这局拿了 {score} 分", force=True)
        if self.ports.audio is not None:
            self.ports.audio.play(ASSETS / "sounds" / "win.wav")

    def stop(self):
        if self._window is not None:
            self._window.close()
            self._window = None

host/game_window.py：窗口与帧循环

from PySide6.QtCore import Qt, QTimer
from PySide6.QtWidgets import QDialog, QLabel, QVBoxLayout


class GameWindow(QDialog):
    def __init__(self, *, on_finish, parent=None):
        super().__init__(parent)
        self.setWindowTitle("桌宠小游戏")
        self.setAttribute(Qt.WidgetAttribute.WA_DeleteOnClose)
        self.resize(520, 420)
        self._on_finish = on_finish
        self._score = 0

        layout = QVBoxLayout(self)
        self.score_label = QLabel("0", self)
        layout.addWidget(self.score_label)

        self._timer = QTimer(self)
        self._timer.setInterval(33)          # 回合制可以完全不启动它
        self._timer.timeout.connect(self._tick)
        self.finished.connect(self._report)

    def start(self):
        self._score = 0
        self._timer.start()
        self.show()
        self.raise_()
        self.activateWindow()

    def _tick(self):
        if not self.isVisible():
            self._timer.stop()
            return
        self._score += 1
        self.score_label.setText(str(self._score))

    def _report(self, _code=0):
        self._timer.stop()
        self._on_finish(self._score)

    def closeEvent(self, event):
        self._timer.stop()
        super().closeEvent(event)

host/store.py：原子存档

import json
import os
import tempfile
from pathlib import Path

SCHEMA = 1


def load(path: Path) -> dict:
    try:
        data = json.loads(path.read_text("utf-8"))
    except (OSError, ValueError):
        return {"schema_version": SCHEMA}
    if data.get("schema_version") != SCHEMA:
        return {"schema_version": SCHEMA}
    return data


def save(path: Path, data: dict) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    handle_fd, temp_name = tempfile.mkstemp(dir=path.parent, suffix=".tmp")
    try:
        with os.fdopen(handle_fd, "w", encoding="utf-8") as handle:
            json.dump(data, handle, ensure_ascii=False)
            handle.flush()
            os.fsync(handle.fileno())
        os.replace(temp_name, path)
    finally:
        if os.path.exists(temp_name):
            os.unlink(temp_name)

已知坑与交付清单

这些不是理论风险，是官方样板与审计里已经踩过的。

现象原因修法
窗口一闪就没 / 被压住没有持住引用，或只 show() 没抬升模块级或 runtime 持引用；show() 后 raise_() / activateWindow()
关掉窗口后游戏还在跑定时器没停，或用了全局 on_tickcloseEvent/hideEvent 停表；runtime.stop() 兜底
重新加载扩展后一次点击触发两次旧 runtime 的订阅没注销stop() 里调用于 on_click/on_drop/on_tick 返回的注销函数
设置页里塞棋盘变成一条缝页面内容在 QScrollArea，默认阅读宽 860棋盘/画布自建窗口；设置页只放规则与按钮
浏览器/网页控件 ImportError冻结包只带特定 Qt 模块importlib.util.find_spec 先探测；不可用就不声明该功能
后台线程里弹窗后整个应用卡死worker 线程直接碰了 Qt结果经 scheduler.call_later 回 GUI；窗口只在 GUI 线程建
桌宠掉帧游戏窗口的绘制/解码占了 GUI 线程重活下后台；降低刷新率；不可见就停表
安装后菜单里没有没开 allow_feature_mods、装错目录、或包被停用装到数据目录；设置 → 扩展管理勾选；mods list 看诊断

协作者的交付清单

  1. mods validate ./game.board 干净；mods install 后 mods list 是 enabled 且没有 ! 诊断。
  2. 菜单能开窗；窗口关闭后定时器/线程都停；再开一次不会出现两个窗口。
  3. 设置页能存能取消；dirty() 改过为真、保存后归零。
  4. 存档在 feature-data/game.board/；杀进程重开后能读回；损坏文件不覆盖。
  5. 运行时代码没有 PySide6、没有 petcore.net/api/account/platform、没有 petcore.ui.*（设置页除外）。
  6. 所有定时器走 scheduler 或自己的窗口，stop() 能全部取消。
  7. 打包：ZIP 只留一层 wrapper 目录；不勾选安装器任务时不写盘。
不要把「capabilities 写了」当成安全边界 它只是给人看、给市场看的声明。真正阻止一个恶意 mod 的，是用户有没有把它装进来、有没有打开功能扩展开关。 分发第三方游戏包时请如实告诉用户这一点。
