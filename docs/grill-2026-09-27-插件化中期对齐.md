# 插件化中期 grill：运行边界与官方选装交付对齐

> **决策日期：2026-09-27；状态：Q1–Q5 已由用户确认。**
>
> 本文记录两轮中期 grill 的问题、推荐方案、用户回答，以及正文中的架构、菜单、设置和交付共识；不是新的实现完成报告。Q1–Q2 为用户明确回答，Q3–Q5 为用户接受推荐方案。下文按含义整理，不把摘要冒充逐字对话。
>
> 本文保存两轮对齐的决策依据；现行正文已统一到[总路线图](plugin-roadmap/PLUGIN-DLC-ROADMAP-v5.md)和[功能交付总表](plugin-roadmap/PLUGIN-FEATURE-DELIVERY-MATRIX.md)，不再依赖补充条款覆盖旧路线。官方选装、最小扩展管理和可拔除验收是硬目标；第三方生态、Workshop、复杂远程分发仍可条件化。已有实现和稳定性证据不改写为新目标已经完成。

## 1. 一句话结论

**继续拆运行边界，同时尽早完成一个真正可安装、可卸载的官方功能样板；最终以最小 Core 不携带选装功能专属实现和依赖为硬验收，而不是以新增了多少 Worker 或插件文件作为进度证明。**

必须分别判断四件事：

- 独立进程不等于独立交付的 DLC；
- 进程隔离不等于安装包已经去掉功能专属依赖；
- 关闭功能不等于卸载功能；
- ZIP 解压运行不等于配置、DLC 和数据已经实现完整便携。

## 2. 两轮问题与最终决策

| 问题（摘要） | 推荐方案 | 用户确认与最终边界 |
|---|---|---|
| Q1：过去主要拆运行边界，是否符合目标？下一步如何证明没有跑偏？ | 保留渐进拆边界，同时增加真正可拔除的交付样板。 | 用户认为减少适当耦合是必要前提，可以先拆边界、不必赶进度；两条线应并行，先做出一个可拔除功能，不能只证明内部拆分数量。 |
| Q2：最终验收是“不安装就没有该功能及其专属依赖”，还是“都装着、可以关闭”？ | 以前者作为硬验收；官方选装必做，第三方生态仍条件化。 | 用户选择前者，并提出 Setup 可选安装、ZIP 按路径放置、主桌宠内卸载的交付要求。最小 Core 与可选的全量离线套装必须分开计量。 |
| Q3：先用哪个功能验证可拔除交付？ | “屏幕理解”作为第一份样板，将自动识屏与手动“看看屏幕”放入同一官方功能 DLC。 | 按推荐方案执行。包内可以有两个独立功能开关，但卸载该包后两者都不应残留。包 ID、版本格式及实际目录尚未冻结。 |
| Q4：Setup 首版如何实现选装，而不先建设下载平台？ | 小 Core Setup + 旁置本地官方 DLC 包，由安装向导选择。 | 按推荐方案执行。首版不以在线 catalog、商店或 Workshop 为前置条件；选择导入仍须通过统一安装事务与校验。 |
| Q5：ZIP 版的数据和 DLC 是否跟着程序走？ | 提供显式便携模式，与普通安装模式区分。 | 按推荐方案执行。普通配置和 DLC 可随目录迁移；密钥仍走安全存储，不为便携写入明文。换机器可能需要重新授权。具体启用方式和只读目录处理另行设计。 |

“两条线并行”是路线安排，不要求在同一批提交中同时重构和改打包。每个主题仍须小步验证、独立回滚。

## 3. 对过去工作的共同判断

| 已有工作 | 保留的价值 | 不能由此宣称的成果 |
|---|---|---|
| Phase 1 资源 DLC | `CharacterRegistry`、`ContentManager`、本地目录/ZIP、安装事务和 fallback 为资源交付建立基础。 | 不等于可执行功能包已经能独立安装；资源包不能借此执行任意代码。 |
| Phase 2 官方插件运行时 | 受限 Context、配置命名空间、事件总线、生命周期和官方节日提醒验证了宿主边界。 | 不等于任意第三方 SDK、动态设置页注册或最小 Core 包体拆分已经完成。 |
| Phase 3A Agent Link Worker | 隔离日志读取、解析与事件采集，具备进程宿主、故障恢复及稳定性证据。 | 没有把完整 Agent Link、展示 UI、bridge 安装管理全部迁出。 |
| Phase 3B 主动识屏 Worker | 自动与手动识屏分离策略/执行边界，沿用同一程序启动子进程及本地 JSONL 通信。 | 目前仍是随 Core 发布的内置能力，不是可选安装、可物理卸载的功能 DLC。 |

用户在本次对齐前反馈：“识屏无误，手动测试没问题”。这是**用户报告的手动体验结果**，应保留；不能替代冻结产物裁剪、安装卸载、故障路径或三平台的独立验收，也不意味着本轮重新执行了这些验证。

因此不回滚 Phase 1–3 的既有成果，也不立即重写整个项目。需要补上的不是更多“拆成一个进程”的数量指标，而是从构建产物到安装、注册、移除的完整闭环。

## 4. 后续两条线及路线优先级

```text
稳定 Core + 官方功能真正选装（硬目标）
├─ 运行边界线
│  ├─ 维护 Phase 1/2/3 的兼容与稳定性
│  ├─ 继续减少私有对象、全局配置和展示逻辑的耦合
│  └─ 根据风险与收益决定其他能力是否需要 Worker
└─ 可拔除交付线
   ├─ 第一份“屏幕理解”官方功能包
   ├─ 最小 Core 产物及依赖清单
   ├─ Setup 本地选装、ZIP 导入与便携模式
   ├─ 菜单、设置、命令按安装状态注册
   └─ 禁用、卸载、重装、升级、回滚验收

条件分支：第三方 SDK / 社区生态 / Workshop / 复杂远程分发
发布门：平台适配 / 安全发布 / 兼容矩阵 / 性能与恢复证据
```

- 保留 Phase 1–7 编号，不用重新编号掩盖历史工作；后续实施计划应把“官方选装交付”明确排入近期样板，而不是无限延后到生态阶段。
- Phase 4 的本地事务继续复用，不能重做一套；远程更新中心可以后置，但最小安装、卸载、状态诊断入口不能因为“管理 UI 条件化”而缺席。
- Phase 5 的来源扩展可按需，但 Setup 本地选装、ZIP 本地导入和官方功能的独立交付属于本次确认的硬目标。
- Phase 6 的第三方生态继续条件化；不开放任意第三方 Python 代码进入 Core 进程，不承诺 Python 热卸载。
- Phase 7 的跨平台发布验收仍是发布责任，不要求每个开发小步都完成三平台实机，也不因生态后置而取消发布门。
- 具体排期、分支、构建方式和提交拆分尚需后续实施方案；本记录不授权立即扩大当前施工范围。

## 5. “可拔除”所要求的 Core / 功能边界

### 5.1 Core 保留通用宿主能力

Core 保留生命周期、基础桌宠交互、窗口动画、配置和迁移底座、权限与安装状态管理、事件总线、通用 Worker 宿主、展示端口，以及菜单/设置/命令的注册宿主。

**在 Core 进程执行，不等于永远属于最小 Core 安装包。** 当前为迁移兼容而放在主进程的功能专属策略、适配器、设置定义和展示绑定，后续也要审计归属，不能只移走截图/网络执行而把其余功能永远硬编码在 Core。

### 5.2 官方功能包拥有专属内容

“屏幕理解”包可以包含受信任的官方宿主侧组件、声明式菜单/设置定义、Worker、专属依赖和资源；不强制一个功能只能对应一个进程，也不强制所有代码都塞进 Worker。

- Core 的通用权限和状态仍是权威；功能不能绕过用户许可、全局限制或直接读写 Core 私有对象。
- Worker 是独立操作系统进程，通过 Core 管理的本地 `stdin/stdout` JSONL 连接，不直接访问 Qt UI；**进程独立不代表安全沙箱**。
- 目前“同一可执行文件 + QProcess”是运行边界方案，不自动满足独立包体要求。最终采用独立 Worker 产物或其他受控加载方式，须由依赖/冻结构建验证决定。
- 资源 `content` DLC 继续只装数据。可执行功能 DLC 必须另有入口、权限、兼容、签名信任和生命周期合同，不能改个扩展名就复用资源安装器执行代码。
- 签名/哈希校验和可信官方发布应与可执行包的风险匹配；“只装本地 ZIP”不等于可以跳过信任确认。

### 5.3 fallback 不得绕过卸载

现有 `in_process` fallback 在迁移期仍有价值；但最终拆包后，fallback 的实现也须属于相应功能包，或在包不存在时不可用。

必须区分：

```text
功能已安装但 Worker 故障 → 可诊断、可恢复或受控 fallback
用户禁用功能             → 停止该功能，不擅自恢复执行
用户未安装 / 已卸载      → 功能不存在，不以隐藏内置实现“补回来”
```

只要卸载后仍从 Core 偷偷启动原有识屏线程，就不算通过可拔除验收。Core 更新也不得删除用户 DLC，或悄悄重装用户已经卸载的功能。

## 6. 菜单、设置与注册生命周期

**现在约定注册边界，完整菜单布局可晚些调整；不能等所有功能拆完才考虑如何接入 UI。**

Core 保留稳定的基础菜单、基础设置、扩展管理和退出；功能包通过受限的贡献接口声明命令、菜单位置、设置页/分组、搜索项与快捷键。托盘和桌宠右键尽量复用同一命令模型，不能在 `PetWindow` 中为每个 DLC 不断添加硬编码分支。

| 安装/运行状态 | 功能菜单与快捷键 | 设置与管理入口 |
|---|---|---|
| 未安装 | 不显示该功能的操作，不保留无效快捷键。 | 不显示其专属设置页/搜索项；扩展管理可显示可安装项。 |
| 已安装且启用 | 在固定扩展位置注册可用命令。 | 注册专属设置；打开设置本身不启动截图或网络 Worker。 |
| 已安装但停用 | 不提供会执行停用功能的动作。 | 保留扩展管理中的配置、启用和卸载入口，不把停用伪装成未安装。 |
| 故障/不兼容 | 不保留点了无响应的动作。 | 在扩展管理显示原因和修复、回滚、卸载入口。 |
| 已卸载 | 移除属于该包的动作、快捷键和订阅。 | 移除专属设置页/搜索项；默认保留用户数据，重装时恢复偏好。 |

注册信息必须有稳定的所属包 ID、命令/页面 ID、撤销句柄和冲突处理；停用/卸载时按所有者统一清理。菜单排序和自定义偏好不应因暂时缺包而被静默破坏。

还须区分：

- 自动识屏开关关闭，不等于整份“屏幕理解”包卸载；已安装时手动“看看屏幕”可以继续可用。
- 设置是否存在取决于包安装、兼容性和权限，不取决于 Worker 此刻是否正在运行。
- 可以借鉴 VPet 的插件贡献和生命周期思路，但这是学习方向，不照搬框架、对象注入或私有 UI 访问方式；Workshop 是来源适配，不是插件运行机制的前置条件。本轮未重新调研其源码。

## 7. 安装、ZIP、便携与卸载的目标体验

### 7.1 Setup：第一版走本地选装

首版交付示意，**不是已实现的文件名或目录合同**：

```text
发布目录/
├─ Core-Setup.exe
└─ dlc-packages/
   └─ 官方屏幕理解包.zip
```

安装向导中的 Core 为必装项，官方功能包为可选项。未选功能包时，Core-only 安装不能携带它的专属实现和依赖。旁置包不存在或校验失败时，应给出清晰提示，不能阻止安装纯 Core，也不能伪装选装成功。

最小 Core 下载物本身不内嵌所有功能；可以另外提供全量离线套装，但其总下载体积不能拿来冒充最小 Core 的体积。

### 7.2 ZIP：按路径放置也要经过安装事务

支持通过应用选择本地包，或放进约定的导入目录后由应用发现。目标流程：

```text
发现本地包
→ 显示名称、版本、来源和所需权限
→ 用户确认 + 完整校验
→ 安装到受管理的版本目录
→ 激活 / 自检
→ 注册菜单和设置
```

“放到路径下”不表示把文件直接覆盖进 Core 的 `_internal`，也不表示把未知 ZIP 放进去就自动执行。用户不需要手写 manifest、`active.json` 或注册配置。

### 7.3 普通模式与显式便携模式

普通模式使用平台用户数据目录；便携模式让普通配置、DLC 和数据随应用目录迁移。示意如下，**不是当前目录已经迁移，也不是最终命名承诺**：

```text
<选定的数据根>/
├─ content/                 # 纯资源 DLC，沿用资源事务边界
├─ plugins/
│  └─ <屏幕理解包-id>/
│     ├─ versions/<version>/
│     ├─ active.json
│     └─ previous.json
├─ data/                    # Core / 实例 / 功能的用户数据
└─ staging/                 # 安装临时区，不是直接加载目录

普通模式的数据根：平台用户数据目录
便携模式的数据根：应用目录内的显式便携数据目录
```

安全存储不承诺随目录移动；不能为了便携把 API Key 明文写进 ZIP 或配置。便携开关/标记文件、首次迁移、只读目录、多个实例和换机器重新授权，需要后续设计与验证。

### 7.4 一套权威安装状态，多个入口

Setup、本地 ZIP 导入和主桌宠扩展管理必须共用同一包生命周期、校验与安装状态语义，不能各自维护一套 active 版本或互相覆盖文件。可以有不同前端，不要求安装器本身导入 GUI。

应用内卸载目标：

```text
阻止新任务
→ 取消请求、停止 Worker
→ 撤销菜单 / 设置 / 命令 / 快捷键 / 订阅
→ 删除受管理的该包文件
→ 默认保留配置与用户数据
```

清除用户数据是另一个明确确认的操作。若宿主组件已加载、其他实例占用或 Windows 文件锁导致不能立即物理删除，必须显示“待重启完成卸载”，重启后再次验证文件和入口消失；不能仅关闭进程就显示“卸载完成”。

安装、升级和回滚复用现有 staging、兼容/哈希校验、active/previous、自检与恢复思路，同时补足功能包的权限与执行边界；不重复造一个与 Phase 1 无关的事务系统。

## 8. 第一份可拔除样板的硬验收

以下是后续实现的验收标准，**不是本轮已通过的测试列表**。

| 场景 | 必须观察到的结果与证据 |
|---|---|
| 纯 Core 产物 | 清单、import 和依赖审计证明没有“屏幕理解”专属实现、资源及专属依赖；共享的 Core 依赖不为做样子而重复拆装。 |
| 未安装、离线启动 | Core 能显示桌宠并完成基础交互；没有识屏入口、专属设置和识屏 Worker，也不会截图或访问视觉服务。 |
| Setup / ZIP 本地安装 | 两个入口安装同一种受管理功能包；版本、权限、校验、自检和失败回滚语义一致。 |
| 安装后启用 | 自动识屏与手动“看看屏幕”可用，菜单/设置正确注册；未获授权时不执行截图或模型请求。 |
| 故障与停用 | 故障不拖垮 Core；停用不执行功能；故障 fallback 不越过禁用或未安装状态。 |
| 应用内卸载 | 停止任务/进程、撤销贡献、删除包专属文件；需重启的如实标记并在重启后验收。 |
| 卸载后启动 | Core 正常，功能入口/专属依赖不残留；不存在隐式启用旧实现的 fallback。 |
| 重新安装与更新 | 默认恢复保留的配置；升级失败可回滚；Core 更新既不破坏 DLC，也不重新装回已卸载功能。 |
| 便携与多实例 | 普通配置/DLC 按所选模式定位；安全存储不泄漏；多实例占用、只读目录和迁移失败有可恢复行为。 |
| 交付证据 | 记录 Core 与功能包各自下载/安装体积、启动/RSS、Worker 数量和卸载前后文件/菜单变化；不能只给文件拆分数。 |

核心闭环为：**不装也能用 → 安装后出现并可用 → 卸载后彻底消失且 Core 仍可用 → 重装恢复配置**。

## 9. 尚待设计的细节与风险

这些不是重新询问已经确认的 Q1–Q5，也不阻塞本轮记录，但不能当成已经决策或实现：

1. 独立可执行产物与运行时的打包方式、官方宿主组件的受控加载方式，以及最终依赖裁剪清单。
2. 功能 manifest、UI contribution/命令合同、包 ID 和版本兼容、权限审批、可信签名与发布流程。
3. 便携模式的启用标记、固定路径、只读处理、普通模式迁移和 keyring 跨机器限制。
4. 多实例共同使用功能时的停止/卸载协调，重启完成卸载和部分失败后的恢复规则。
5. 菜单/设置最终布局、默认选装项，以及现有快捷键和自定义顺序的迁移规则。
6. 跨平台交付顺序、实施里程碑、分支和提交拆分；不能以 Windows Setup 样板替代其他平台发布验收。

下一份实施计划应先检查“如果把这份功能包整个移走，Core 哪些 import、页面、配置或启动路径会出错”，再冻结最小包合同；不要先写商城，也不要机械地把所有功能都进程化。

## 11. 面向用户的最终效果说明

你将能先只装“桌宠本体”：角色、动画、拖拽、托盘和基础交互照常工作，没有“屏幕理解”的代码包、专属设置或后台进程。

想让它看屏幕时，在 Setup 勾选旁置的官方包，或以后在桌宠里导入本地 ZIP。装好后，自动识屏设置和“看看屏幕”菜单才出现；不需要手工改配置注册它们。

不想用了，在桌宠的扩展管理中卸载。后台任务停止，相关菜单和设置消失，功能文件移除；默认保留你的配置，下次重装不用从头配置。若必须重启才能删完，会明确提示，不假装已经完成。

Worker 依然是与 Core 通过本地管道相连的独立进程，不是完全断开的应用；Core 决定权限和展示，Worker 完成截图和视觉请求。

**这些是本轮已经确认、接下来必须交付的目标，不是今天已经支持的安装/卸载操作。** 目前识屏仍是内置 Worker；首先完成一份真正能拔除的样板，再逐步推广到其他官方选装功能。

| 性质 | 本轮记录 | 如何落到计划 |
|---|---|---|
| 已确认硬要求 | 运行边界和真正可拔除交付并行；官方功能可选安装必须完成。 | Phase 4A/4B 做首个样板，Phase 5A/5B 推广正式交付，不把全部功能先 Worker 化作为前置。 |

### AI 不再是遗漏项，也不是把全部模型能力塞回 Core

- Chat QWidget 暂不强制迁到独立进程，但聊天专属 UI、会话策略、设置和快捷对话随 AI 功能包交付；运行在主进程不等于属于 Core 安装包。
- Provider、流式请求和网络执行单独评估 Worker；现有 QThread 不算独立操作系统进程。
- 会话、角色/实例隔离、附件与安全存储要有备份、迁移、重装恢复证据。文件理解仅承接现有附件/文本文件解释，不承诺尚不存在的通用 PDF 或二进制解析。
- 屏幕理解可不安装 AI 对话而独立配置视觉服务；同步聊天是可选联动。安装 AI 对话不自动获得截图权限，也不依赖灵动岛。
- 模拟投喂与 AI 文件解释分属不同功能所有者；模拟投喂不得移动、删除或修改用户真实文件。

### 同步到所有计划的验收句

> 不安装也能启动 Core → 安装后入口出现且可用 → 停用后不执行 → 卸载后文件与入口消失 → 重装恢复保留配置。

同时验收专属依赖、离线启动、多实例、权限、升级回滚和实际体积。fallback 只能服务于已安装、启用且获授权的功能；不能因为包不存在就偷偷恢复进程内实现。Core 更新不能重新装回已卸载功能。

## 13. 本轮修订后的直白结论

你可以在功能总表中逐项找到“本体保留什么、哪个功能需要另装”；先完成能真正移走的识屏包，再重点拆 AI 对话，不会漏掉聊天。没装的功能不应在菜单、设置搜索或后台出现；安装后才注册，卸载后撤销，数据默认保留。

官方功能包以后可以同时带主进程 UI/策略和独立 Worker，两者通过受限宿主接口及本地 JSONL 管道合作。文件将落到受管理的功能包版本目录，不混入角色资源目录；确切包格式和路径在 Phase 4A/5A 确定。Setup 选装、导入 ZIP 和应用内卸载都必须使用同一套状态与事务。

**这次完成的是文档和验收目标对齐；当前内置 Worker 还不等于可安装、可卸载的官方功能包。**
