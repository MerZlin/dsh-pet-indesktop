# PR 报告模板（`docs/PR-REPORT-<主题>-<YYYY-MM-DD>.md`）

> **怎么用**：把本文件整份复制成 `docs/PR-REPORT-<主题>-<YYYY-MM-DD>.md`，逐节填写，
> 然后在 [`INDEX.md`](INDEX.md) 的「PR 报告存档」登记一行（新文档入场规则第 1 条）。
> PR 描述里放摘要 + 指向本报告的链接，不要把报告全文粘进 PR。
>
> **三条硬要求**（2026-09-22 起，见 [`../AGENTS.md`](../AGENTS.md) 的
> Delivery evidence discipline 与 [`DEV-HANDOVER.md`](DEV-HANDOVER.md) §8.3）：
> 标题必须逐字包含「**修改文件说明**」「**性能分析**」「**实机运行记录**」三节。
> [`../tests/test_pr_report_discipline.py`](../tests/test_pr_report_discipline.py)
> 会对本日期之后的报告强制校验。**纯文档/文案/依赖版本号这类不改变运行行为的
> 改动**可只保留第一节，但必须在 PR 描述里写明豁免理由。
>
> 后续轮次在**同一文档追加新章节**（「第二轮改进」「第九轮修正」），保留新旧对照，
> 不要重写覆盖——评审依赖历史对照。

---

> **基线**：`<sha>`（<它是什么，如 Merge PR #NNN>）
> **分支**：`<branch>`　**日期**：`<YYYY-MM-DD>`
> **范围**：N 个文件（实现 x、测试 y、文档 z）
> **关联**：<上游/相关报告或 issue 的链接>

## 一、核心特性

一段话讲清「解决什么问题 / 用户看到什么变化」。若根因是可测量的，把测量结论
写在这里（例如「某播放器不上报进度」要有实测输出，不能只是推断）。

| # | 能力 | 说明 |
|---|---|---|
| 1 | | |

**红线 / 不变量**：本改动不允许被破坏的既有语义是什么。

## 二、修改文件说明

逐文件写「改了什么 + 为什么」，给出增删行数（`git diff --numstat`）。新增与删除
的文件都要列出。**不要只写「修了 bug」**——写清楚哪个函数、哪条分支、为什么。

### 实现

| 文件 | 增删 | 改动意图 |
|---|---|---|
| `pet/xxx.py` | +N / −M | |

### 测试

| 文件 | 增删 | 覆盖 |
|---|---|---|
| `tests/test_xxx.py` | +N / −M | |

### 未改动（可选但推荐）

明确写出「看起来相关但故意没动」的文件，避免评审误以为漏了。

## 三、实现要点

关键算法、数据结构、线程与信号模型、为什么这么设计。取舍与备选方案一并写。

## 四、性能分析

**必须有实测数字**（命令 + 环境 + 样本量）。没有数字的分析不算分析；
用「可忽略 / 更快 / 优化了」替代数字视为没写。

**方法（可复现）**：`<完整命令>`　环境：`<OS / Python / 关键版本>`

| 指标 | 实测 | 归属（热路径 / 新增 / 既有） |
|---|---|---|
| | | |

**结论**：逐条回答——① 稳态开销有没有变化、变了多少；② 新增路径的绝对成本与
触发频率；③ 有没有引入新的系统调用 / 网络 / 磁盘 / 线程；④ 内存与缓存有没有增长。
若本改动有基准脚本，写明脚本路径，方便后来者用同一条命令复测。

## 五、实机运行记录

**本机真实环境**跑过什么（不是 CI、不是 mock）。写命令与真实输出，写不出来就说明
为什么写不出来。至少覆盖：

- **根因/前提的现场复现**：命令 + 原始输出片段（证明这个问题此刻真实存在）；
- **用户可见行为的确认**：谁、在什么操作下、看到什么（用户确认也算，注明）；
- **边界与失败路径**：至少一条「本该失败/本该置灰」的实机观察；
- **无法自动验证的能力**：给出「为什么不能自动」的排查证据（探针结果），
  不要用沉默代替结论。

## 六、测试与验证

| 门 | 命令 | 结果 |
|---|---|---|
| 静态检查 | `python -m ruff check pet tests scripts` | |
| 聚焦 | `pytest -q <files>` | |
| 受影响时序族满载 3 遍 | | |
| 全量 | `python -m pytest -q` | |
| 断言有效性（可选） | 临时注入缺陷重跑，证明断言能区分新旧实现 | |
| 架构红线 | `tests/test_architecture.py` | |

## 七、已知限制与后续

明确写出未完成项与不打算做的事，以及触发条件（例如「播放器开放进度上报后，
该入口会自动置灰，无需改代码」）。

## 八、风险与回滚

影响面、开关、配置迁移（有没有新增键）、回滚步骤（`git revert` 后会不会有残留
状态或落盘数据）。
