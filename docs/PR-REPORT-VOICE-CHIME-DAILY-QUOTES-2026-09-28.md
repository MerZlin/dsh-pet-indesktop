## 一、核心特性

用户反馈：「桌宠的报时功能台词几乎每天都是一样的」。

根因在 v2 的批次算式本身：**批次 =（日期序数 × 3 + 当日第几段）% 3**。
`× 3` 与 `% 3` 恰好对消——日期维度被自己抵消，批次只由「当天第几段」决定，
于是**每天同一时刻永远是同一句**，40 条台词在 14/13/13 三批里来回打转。
这不是库太小，是算式把天抹掉了。

| # | 能力 | 说明 |
|---|---|---|
| 1 | 每天一整套新排列 | `quote_day_order(pool, day_ordinal)` 以日期为种子做确定性洗牌，当天固定、跨天整套换新 |
| 2 | 日内顺序取用 | `pick_quote` 取当天排列第 `chime_index_in_day % 库长` 条，顺序用尽回环 |
| 3 | 台词库扩容 | 中文 40 → **120**、英文 40 → **96**，盖得住每 15 分钟一天 96 次而不重句 |
| 4 | 回溯改算术 | `chime_index_in_day` 逐模式直接算出当日第几次报时，不再逐分钟扫描 |

**红线 / 不变量**：
- 同一时刻语音与气泡必须取到**同一条**台词（两处各自调用 `pick_quote`，故它必须是
  `now` 的纯函数，不能带状态/随机）；
- 同一分钟内重复 tick 结果必须一致（槽位盖戳之外的第二道幂等）；
- 自定义台词非空时仍**整体替换**内置库；`show_quote=False` 时仍只报时间。

## 三、实现要点

1. **确定性洗牌不依赖 `random`**：`random.shuffle` 的可复现性只对 `random()` 有形式
   保证，`_randbelow` 走 `getrandbits`；库升级换实现就会让「今天取哪句」漂移（还会
   连带让已合成的缓存键对不上）。故自带 64 位 LCG（Knuth/MMIX 常数）+ Fisher–Yates，
   取**高 31 位** `state >> 33` 而非低位取模，避开 LCG 低位周期短的排列偏差。
2. **为什么不是「每天加一个随机偏移」**：偏移若取 `每天报时次数 % 库长`，与库长不互质
   时会把「同一时刻」锁进很短的轨道（如 96 % 40 → 轨道只有 5 天）。洗牌把「日内次序」
   与「跨天差异」解耦：日内不重句、跨天整套换序，同一时刻跨天实测 9 天全不同。
3. **日内次序用算术而非回溯**：v2 的 `chime_index_in_period` 从周期起点逐分钟判定，
   最坏 480 次 `is_chime_minute`；新实现按模式一行算出（`every_15` → `hour * 4 + minute // 15`），
   自定义时间点用「≤ 当前时刻的条数 - 1」。这也是本次唯一的性能动机（见第四节）。
4. **库长取 96 的依据**：设置里最高频的现实配置是「每 15 分钟」= 96 次/天，故两个库
   都不得短于 96；中文库取 120 留出余量，英文库补到 96。`tests` 里有 `len(...) >= 96`
   护栏，防止后来者删条目时悄悄退化。
5. **删函数不删语义**：`split_quote_batches` 等三个纯函数无其它引用点（全仓 grep 确认），
   直接删除而非保留空壳。

## 四、性能分析

**方法（可复现）**：性能与行为数字由 `bench` 脚本采集——把**父提交**（上游 `2786c15`）
的 `pet/voice_chime.py` / `pet/voice_chime_quotes.py` 导出成模块，与分支实现同进程对照：

```
git show 9040338^:pet/voice_chime.py         > old_voice_chime.py
git show 9040338^:pet/voice_chime_quotes.py  > old_voice_chime_quotes.py
python bench.py        # timeit，样本 20000 次/项
```

环境：`Windows 10 (26100)` / `Python 3.11.9` / `PySide6 6.11.2`；调度 `every_15`
（一天 96 次报时）；库长 旧 40+40 条、新 120+96 条。

| 指标 | 旧实现 | 新实现 | 归属 |
|---|---|---|---|
| `pick_quote` 单次 | 79.9 µs | **24.1 µs** | 热路径（每次报时 2 次：语音 + 气泡） |
| ├ `quote_day_order`（新增） | — | 21.2 µs | 新增路径 |
| ├ `chime_index_in_day` | — | 0.2 µs | 替换旧 `chime_index_in_period` 的 75.4 µs |
| `build_chime_sentence` 端到端 | — | 25.1 µs | 热路径 |
| 同一时刻 7 天去重（09:00） | **1 / 7** | **7 / 7** | 行为指标 |
| 单日 96 次去重 | **40 / 96** | **96 / 96** | 行为指标 |
| 两个库常驻内存 | 8.0 KiB | 21.3 KiB（+13.3） | 常驻 |
| 每分钟调度下同一句重现间隔 | 14 分钟 | 120 分钟 | 边界 |

**结论**（逐条回答模板要求）：
1. **稳态开销**：`pick_quote` 79.9 → 24.1 µs（−70%）。每天 96 次报时 × 2 处调用，
   合计每天省约 `96 × 2 × 55.8 µs ≈ 10.7 ms`；相对 20 s tick 的调度器与 TTS 合成
   （百毫秒级）属噪声级，但方向是变快而非变慢。
2. **新增路径成本与频率**：新增 `quote_day_order` 21.2 µs/次，触发频率 = `pick_quote`
   调用频率（每 15 分钟 2 次）；库 120 条时洗牌 119 次交换，成本随库长线性、与时间无关。
3. **系统调用 / 网络 / 磁盘 / 线程**：**无新增**（纯内存计算，无 IO、无线程）。
   **但有一处间接的稳态变化**：旧实现每天只有 40 条不同文本，稳态下（库已被缓存覆盖）
   一天 0 次新合成；新实现每天最多 96 条不同文本 → 稳态每天最多 96 次在线合成请求
   （`edge-tts`，每条约 30 KB 音频；实机缓存目录当前 200 个文件 / 17.9 MB，上限
   `MAX_CACHE_FILES = 200` 未变）。这正是「每天不一样」的代价，非缺陷。
4. **内存与缓存**：库内存 +13.3 KiB（进程常驻，一次性）；磁盘侧缓存仍受 200 条上限与
   5 分钟节流的裁剪约束，**上限与算法均未改动**，不随库长增长。

## 七、已知限制与后续

- 库长仍是「多久重句」的硬上限：每分钟调度下 120 条 = 120 分钟一轮。想更长只需往
  `pet/voice_chime_quotes.py` 追加条目（无需登记配置，洗牌只看库长）。
- 每天新增合成请求见第四节结论 3；若担心在线合成次数，可把报时频率调成整点（24 次/天）。
- 不打算做：按天气/情绪/日程挑台词——没有本地数据源，且用户诉求是「每天不同」而非
  「按情境不同」。

## 八、风险与回滚

- **配置迁移**：无新增/删除配置键，`config.json` 不需要迁移；旧值语义不变。
- **影响面**：仅报时台词选取；调度、合成、播放、气泡、缓存层均未触碰。
- **回滚**：`git revert <merge>` 即可；`cache_key` 只按文本+音色参数计算，旧缓存文件在
  回滚后依然有效（新句子产生的缓存会按 200 条上限自然裁剪，无残留状态）。
- **上游适配**：本改动以父提交为基线重做（cherry-pick），只依赖上游已有的
  `CHINESE_QUOTES`/`clean_custom_quotes`/`DEFAULT_VOICE`，不引用任何私有定制模块。
